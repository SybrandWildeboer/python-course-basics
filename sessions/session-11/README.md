# Session 11: Project scoping and setup

**Goal:** they leave with a chosen question, a working repo, and something trivial already
running end to end.

**Slides:** [`slides/session-11.html`](../../slides/session-11.html) (15 slides)

**Do not let this become a planning session.** A beautiful plan and no code is the failure
mode. The whole point is that they start before they leave.

## The block that matters: 0:30 to 1:00

Something working end to end today, however trivial, means the remaining work is
**modification rather than creation from nothing**. Those are very different feelings on a
Tuesday evening with an hour to spare.

The deliverable for that block is a committed, pushed script that loads the data and prints
the row count. Not the analysis. Do not let them skip ahead.

It proves five things that could each have eaten an evening: the repo exists and they can
push, the venv works and pandas is in it, the data is where they think it is, the path works
from any folder, and the file runs.

## Scoping: be annoying about it

First ideas are almost always three projects wearing a coat. Push hard, and be warm about it.

The target shape:

> "Using dataset X, answer question Y, producing a chart and a short written conclusion,
> generated by a script that runs start to finish."

Requirements, all three non-negotiable:

- they **already have the data**, or can download it in ten minutes
- it uses a database, pandas, and at least one chart
- it is answerable in the hours they actually have

**The test:** can they say what "done" means in one sentence? If not, it is not a project
yet, it is an area of interest.

Then agree **minimum, target and stretch** out loud, and get them written into the README.
Naming the minimum is what means a bad fortnight still ends in a finished project. Naming
the stretch is what stops it quietly becoming the target.

## No notebooks this session

By design. They work in **their own** project from now on, and the exploring happens in
`notebooks/` in their repo rather than in this one. `project/notebooks/README.md` has the
two lines they need about importing from `src/`.

## Watch out for

- **A project that needs data they do not have.** The most common way these fail. If the
  data is not already on their machine or ten minutes away, change the project, not the
  timeline.
- **Scope creep disguised as ambition.** Enthusiasm is the raw material; your job is to aim
  it at something finishable.
- **Planning for two weeks and coding for zero.** Hard stop the milestone block at fifteen
  minutes.
- **A question with no answer.** "Find interesting patterns" has no "done".
- **A question where only one answer is interesting.** That is an argument, not an analysis.
- **Their data turning out to be unusable.** This is the best possible outcome of this
  session, because there is still time to change. Much better than discovering it on day 9.

## Before they close the laptop

- [ ] Question at the top of the README
- [ ] Minimum, target and stretch written down
- [ ] Repo on GitHub with a pushed commit
- [ ] venv, and `requirements.txt`
- [ ] Data in `data/`, with a note on where it came from
- [ ] A script that runs and prints the row count
- [ ] Four or five milestones with rough dates
- [ ] **Session 12 in their calendar**

## The two-week gap

Confirm the date and time explicitly, and watch them add it to the calendar. Two-week gaps
are where sessions get lost.

Tell them now what session 12 looks like: they present for 15 to 20 minutes, then you review
the code together and improve two or three things live. People write noticeably tidier code
when they know somebody will read it back to them, and saying so is fair rather than
manipulative.

Saturday check-in continues: one line, `On track` or `Not on track`.
