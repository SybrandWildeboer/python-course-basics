The problem

Why bother? Look at what you already have.

Your statistics file has four calculations in it. Suppose you now want the same four for a second list of numbers.

With what you know today, you copy and paste the whole block and change the variable names. Then you find a bug in the highest calculation and have to fix it in both places. Then there is a third list.

A function is a named piece of work you can run again with different input. Write it once, fix it once, use it anywhere.

You have used functions all along

print(), len(), int(), input(), random.randint(). Somebody wrote each of those, and you just call them. Today you join in.

Three good reasons

  • No copy and paste, so one fix is one fix
  • A name explains what a block of code is for
  • You can test a small piece on its own

Anchor this in their own file rather than an abstract example. "You would have to copy all of this" is much more persuasive when it is their code on screen.

Part one

The mechanics

Eight small ideas. The third one is the one that matters, so we will slow down there.

Idea 1

def: defining and calling

Two separate moments

Defining the function teaches Python the recipe. Nothing happens yet. Calling it, with the brackets, is what runs the recipe.

▲

The two classic slips

  • Defining a function and never calling it. The file runs, nothing happens, no error.
  • Writing greet instead of greet(). Without brackets you are talking about the function, not running it.

Have them type print(greet) to see the function object printed. It makes "with brackets, without brackets" concrete rather than a rule to remember.

Idea 2

Parameters: giving the function something to work with

Two words for the same slot

The parameter is the name in the def line. The argument is the actual value you pass in when you call it. Nobody minds if you mix the words up.

Passing by name, as in describe(age=41, name="Sam"), is worth the extra typing when a function takes several things and the order is not obvious from reading the call.

Keep this short. Parameters rarely confuse anybody. The next slide is the one that matters.

Idea 3 · the important one

return is not print

prints, returns nothing
returns a value you can use
◆

print shows a human. return hands a value back to your program. A function that prints is a dead end: you can look at the answer but you cannot do anything with it. A function that returns can be added up, sorted, passed into another function, or written to a file.

Do not move on from this slide until they can predict the output of all six lines. Have them type both versions and try to use the result in a calculation. The moment they see None + 1 fail is the moment it clicks.

Rule of thumb to give them: functions that calculate should return. Only the outermost part of your program should print.

Idea 4

No return means None

None means "nothing here"

It is a real value that represents absence. It is not zero, not an empty string, and not an error.

▲

The bug to remember

An if with a return inside it and no else will hand back None whenever the condition is false. Then some line far away fails with "NoneType" in the message. When you see that word, look for a function that forgot to return.

"NoneType" appearing in an error is the tell. Teach them to treat it as a signpost pointing at a function, not at the line that crashed.

Idea 5

return stops the function there and then

Guard clauses

Deal with the odd cases first and return immediately. What is left at the bottom is the normal case, unindented and easy to read. This is the flattening idea from last week, applied to functions.

Anything written after a return that runs never happens. VS Code will grey it out for you, which is a useful hint that something is wrong.

Connect it back to the nested-if slide from session 2. Same lesson, new tool.

Idea 6

Default values

A default makes a parameter optional. It lets a function have a sensible everyday behaviour and still be adjustable when you need it.

▲

Parameters with defaults have to come after the ones without. def f(a=1, b) is a SyntaxError, and the message tells you so quite clearly.

Do not mention mutable default arguments. It is a genuine Python trap and completely wrong for session 3.

Idea 7

Scope: what happens inside stays inside

Variables inside a function are local

They are created when the function runs and disposed of when it finishes. The rest of your program cannot see them.

That is a feature

It means you can use the name total in ten functions without them interfering. Each one has its own.

The rule of thumb: pass what you need in as parameters, hand the answer back with return. Do not reach out of a function for values.

Do not teach the global keyword. They will find it, it will seem convenient, and it causes the kind of bug that is miserable to find. If asked: it exists, and you almost never want it.

Idea 8

Naming things, and the docstring

Name it after what it gives you

  • average(numbers), not do_calc(x)
  • Verbs for actions: load_data, save_chart
  • Questions for true or false: is_even, has_errors

A docstring is a string on the first line of the function. Tools read it, help() prints it, and your editor shows it when you hover. One sentence saying what comes back is enough.

The naming habit pays off in session 10 when they build a pipeline of load, clean, analyse, output. Good names are what make that structure obvious.

Putting them together

Functions can call other functions

This is the whole idea

Small functions that each do one thing, stacked into bigger ones. average does not know how to add up a list; it asks total. Fix a bug in total and both are fixed.

Notice that only the last line prints. Everything above it returns. That is the shape to aim for: calculate quietly, print once, at the edge.

This slide is the target shape for the live exercise. Point at it again when they are building.

In practice

The same work, before and after

one long script
pieces that fit together
◆

The right-hand version is barely shorter for one list. For two lists it is much shorter, and for ten it is the only version anybody would write. That is the trade: a little structure now, in exchange for change being cheap later.

Be honest that the refactored version is not shorter at first. Overselling it invites scepticism. The win is that it absorbs change.

Useful habit

Check a function on cases you can work out in your head

assert in one line

assert something_true does nothing at all. If it is false you get an AssertionError, straight away, on that line.

Pick the awkward cases

Zero, one, negatives, an empty list. That is where the bugs live. Your highest function from last week was correct for the list you tried and wrong for [-5, -2, -9].

This is the seed of proper testing, which is on the map in session 12 under pytest.

Do not turn this into a testing lecture. The habit to plant is "check the edges on purpose", and assert is just a tidy way to write the check down.

Reference

The five function mistakes, and what they look like

MistakeWhat you seeFix
Defined it, never called itNothing happens, no error at all Add the call at the bottom of the file
Called it without bracketsNothing happens, or something like <function greet at 0x...> printed greet(), not greet
Printed instead of returnedTypeError mentioning NoneType when you try to use the result Swap print(x) for return x
A return inside an if, with no other path None for some inputs and no complaint Make sure every route out of the function returns something
Using a variable from inside a function outside it NameError: name 'subtotal' is not defined Return it, and store what comes back
◆

Three of these five produce no error message at all, which is why they are worth knowing by sight. When a function seems to do nothing, start at the top of this table.

Wrap up

What you can do now

  • Define a function and call it
  • Pass values in as parameters, by position or by name
  • Hand a value back with return, and use it
  • Explain the difference between returning and printing
  • Recognise None and what it usually means
  • Return early to keep logic flat
  • Give a parameter a default value
  • Say why a variable inside a function is invisible outside it
