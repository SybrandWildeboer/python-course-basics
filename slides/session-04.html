Part one

Lists and dictionaries

Many values in order, and values you find by name.

Idea 1

A list holds things in order

Zero is the first

This is why range(5) gave you 0 to 4 last session. A list of 4 items has positions 0, 1, 2, 3. The last position is always len(list) - 1, or just -1.

Negative positions count backwards from the end, which saves you arithmetic. [-1] is "the last one" no matter how long the list is.

IndexError means you asked for a position that does not exist. Add it to your collection of recognisable errors.

The zero-based point connects back to range() from session 2. Make the link explicitly, it turns two arbitrary rules into one idea.

Idea 2

Slicing: a piece of a list

◆

Same rule as range

The end position is not included. nums[1:4] gives you three items, not four. Annoying for a week, then automatic.

One handy use: rows[:5] to peek at the first five rows of a file you just loaded, instead of printing two thousand lines into your terminal. You will do that a lot today.

rows[:5] is the practical takeaway. They will need it within the hour.

Idea 3

Growing, changing, checking

in is worth remembering

One word to ask "is this in there". You will use it constantly, and it reads like English in an if.

sorted() versus .sort()

sorted(x) hands back a new sorted list and leaves x alone. x.sort() rearranges x and returns None. Writing x = x.sort() throws your data away, and it is a genuinely common accident.

The x = x.sort() mistake is the one to show live. It connects straight back to last week: a function that changes something and returns None.

Idea 4

Looping over a list, and the accumulate pattern again

Same pattern as session 2

Set up before the loop, update inside, use after. It does not matter whether you are looping over range(10) or over two thousand rows of real data.

enumerate gives you position and value together. Reach for it when an error message says "row 47" and you want to know which row that was.

enumerate feels like a nicety now and becomes essential the first time they need to report which row of a CSV was malformed.

Idea 5

A dictionary maps names to values

A list asks "which position". A dict asks "which name".

For a row of data, names win every time. play["genre"] still makes sense in six months; play[4] does not.

The names are called keys, the things they point at are values. Keys are usually strings, and each one appears once.

KeyError means that key is not in the dictionary. Usually a typo, or a column name that is not quite what you assumed.

KeyError from a mistyped column name is the error they will hit most this week. Show it now so it is familiar later.

Idea 6

Adding, updating, and .get()

◆

When to use .get()

Use [] when a missing key means something is genuinely wrong and you want to hear about it. Use .get() with a default when missing is a normal thing that happens.

counts.get(genre, 0) + 1 is the counting pattern in one line, and you will write it in the exercise today. It means "whatever is there, or zero if nothing is, plus one".

Do not mention defaultdict or Counter yet. The .get() version makes the mechanism visible, and that is the point today. Mention Counter exists at the end if they ask.

Idea 7

Looping over a dictionary

.items() is the one you will use most. It hands you the key and the value together on every pass.

That last one looks alarming

Copy it, use it, and do not worry about lambda yet. It means "sort by the second thing in each pair". It is the standard way to turn a dictionary of counts into a top-five list, so it is worth having in your notes.

{genre:12} pads to 12 characters and {number:>5} right-aligns in 5. That is how you get columns that line up in a terminal.

Be explicit that the sorted() line is a copy-and-keep recipe, not something to derive. Permission to copy without full understanding, once, is genuinely useful here.

Part two

Files

Until now, every value has been typed into your program. Real data lives on disk.

Idea 8

open(), and why with is the way

with closes the file for you

Even if your code crashes halfway through. Always use it. An unclosed file can hold a lock on Windows and lose data you thought you wrote.

Always pass encoding="utf-8"

Without it, Python guesses based on your operating system. The guess is usually right on a Mac and wrong on Windows, and the symptom is a UnicodeDecodeError the first time somebody's name has an accent in it. Our dataset has Salon Mécanique in it, so this matters today.

The encoding point is not pedantry. It is the difference between their script working on their machine and working on anybody else's.

Idea 9 · the confusing one

Where is the file? Where am I?

■

FileNotFoundError is nearly always this

The file exists. Python is just looking somewhere else. First move: print os.getcwd() and see where you actually are.

Relative paths are counted from the folder your terminal is in, not from the file you are editing. Run the same script from a different folder and the path breaks, which is why this confuses everybody at least once.

The Path(__file__) trick means "wherever this script lives". It comes back later in the course. For today, cd to the repo root and use relative paths.

This slide causes more confusion than the concept deserves. Have them cd around and run the same script from two places to see it break. Then agree on one habit: always run from the repo root.

Idea 10

The csv module hands you rows as dictionaries

◆

DictReader reads the header row and uses it for the keys. What you get back is exactly the shape from two slides ago: a list of dictionaries, one per row. You already know how to loop over that.

The list(...) around DictReader matters: without it you get a reader you can only walk through once, and the second loop silently does nothing. That is a real gotcha worth demonstrating.

Idea 11

Everything from a CSV arrives as text

▲

The same lesson as input()

A file has no idea what a number is. It contains characters. 4.65 in a CSV is the text "4.65" until you say float().

This is genuinely the most common source of bugs when people start working with files. When something numeric behaves strangely, print its type() first.

Session 6 is largely "pandas does this conversion for you", so make the pain vivid now. It makes read_csv feel like a gift rather than magic.

Idea 12 · the pattern of the day

Counting things into a dictionary

◆

Look at what that is: the accumulate pattern from session 2, with a dictionary instead of a single total. In session 5 you will write the same question as GROUP BY genre, and in session 6 as groupby("genre"). Same idea, three notations.

Say the "same idea, three notations" line out loud. It is the spine of sessions 4, 5 and 6, and it makes SQL and pandas feel like translations rather than new subjects.

Idea 13

Writing a CSV back out

Three arguments that matter

  • "w" means write, and it replaces the file without asking
  • newline="" stops blank lines appearing between rows on Windows
  • fieldnames sets the column order

New syntax, one line

[row for row in rows if ...] is a list comprehension: build a new list from an old one, keeping what matches. It is the same as a for loop with an append, written in one line.

Introduce the comprehension but let them write the loop version if they prefer. Being able to read one matters more than writing them right now.

The output folder needs to exist, or they get a FileNotFoundError on write. Worth mentioning: the exercise starter creates it.

Part three · after the break

Git and GitHub

Four sessions of work, safe and off your laptop. Everything from here is typed by you, in the repo you cloned in session 1.

The problem

You already have a version control system. It is just bad.

Everyone has done this. It sort of works, and it fails in exactly the ways you would expect: you cannot tell what changed between two files, you cannot remember why, and you certainly cannot undo one change from last Tuesday while keeping everything else.

What git gives you instead

  • One folder, with a full history
  • A message on every change saying why
  • The exact difference between any two points
  • The ability to go back, safely
  • A copy somewhere that is not your laptop

The honest summary: git is a save button with notes attached, and a time machine you will use about twice a year and be extremely glad of both times.

Ask them if they recognise the file list. They always do, and it makes git feel like a fix for a problem they have rather than professional ceremony.

Mental model

Three places your work can be

Come back to this diagram every time they are confused today. Nearly every git question a beginner has is really "which of these three am I looking at".

Do it now · one time only

Tell git who you are

Every commit carries a name and an email. Without these, git refuses to commit at all, with a message that is friendlier than most.

The other two set sensible defaults: name the first branch main, and merge rather than rebase when pulling. Both save confusion later.

◆

Use the same email as your GitHub account and your commits will link to your profile. Not important, quite satisfying.

Unconfigured user.name is the most common first-commit failure. Do it before anything else today.

Do it now

The loop you will run a thousand times

git status is not a formality

Run it before and after everything, today and for the next month. It tells you which of the three places your work is in, and it usually suggests the command you want next.

Useful shorthands

  • git add . stages everything changed
  • git log --oneline is the readable history
  • git log -3 for just the last three

Have them commit the exercise they finished before the break, for real, right now. A real commit of their own work is worth more than a demo file called test.txt. If they worked in the notebook instead, commit that, after the strip step on the next slides.

Staging is what lets one commit be one idea: the exercise in one commit, the session 3 homework in another. Be honest that git add . is the common case.

Craft

Commit messages: write for future you

unhelpful
useful

The shape that works

Present tense, start with a verb, say what changed and why. Around fifty characters is plenty. If you need more, the commit is probably two commits.

The test: in six months, reading only the message, would you know whether this is the commit you are looking for? "fix" never passes.

They will write "stuff" at least once. Rather than lecturing, ask them to find a specific change in their own log in a few weeks' time. The lesson lands by itself.

Do it now

.gitignore: what should never go in

The rule of thumb

Commit what a human wrote. Ignore what a machine generated, anything enormous, and anything secret.

■

Never commit passwords or keys

Once it is pushed, treat it as public forever, even if you delete it in the next commit. The history keeps it. This is the one git mistake that is genuinely expensive.

This repo already has a .gitignore, so look at it together rather than writing one from scratch. Point out that output/ is ignored, which is why the CSVs they write there, starting with this week's homework, will never show up in git status.

Do it now · budget 20 minutes

Getting GitHub to trust your machine

GitHub stopped accepting passwords for git years ago. You need one of these, and the first is much the least painful.

GitHub CLI

Answer four questions in the terminal, approve it in the browser, done. It stores the credentials for git as well. Start here.

Personal access token

On github.com: Settings, Developer settings, Tokens. Create one, copy it, and paste it when git asks for a password. It is a long random string and you cannot see it again, so save it somewhere sensible.

SSH key

The grown-up option, and the fiddliest to set up. ssh-keygen, then paste the public half into GitHub. Worth doing eventually, not today.

▲

We are doing this now, in the session, not as homework. Credentials are miserable to debug over chat, and this is exactly the kind of thing that quietly kills a week's momentum.

gh auth login also configures the git credential helper, which is why it is the recommendation. If gh is not installed, install it now; it is worth the five minutes.

If everything fails, a personal access token pasted at the password prompt always works. Have them store it in a password manager.

For the homework

Branches: try something without risking anything

A branch is a label on a line of commits

Switching moves your files to how they look on that line. Your work on one branch is invisible on the other until you merge.

What they are for

Anything you are not sure about. If it works, merge it. If it was a bad idea, delete the branch and nothing on main ever knew.

Working solo you will mostly live on main. Branches matter enormously with other people. Homework task 3 walks you through one.

Two minutes, as part of the homework briefing. Homework task 3 is exactly these commands with a real file, so they will see "Fast-forward" for themselves. Merge conflicts are out of scope today; mention they exist and are survivable, and that the git stretch notebook makes one on purpose.

Reassurance

Getting out of trouble

You want toType
Throw away changes to one file, back to the last commit git restore path/to/file.py
Unstage something you added by mistake git restore --staged file.py
Undo a commit by adding an opposite one git revert <commit>
Look at how a file was three commits ago git show HEAD~3:file.py
See what on earth is going on git status, then git log --oneline
◆

The thing to actually remember

Once something is committed, it is very hard to lose. Git keeps almost everything, including things you think you deleted. If you get into a mess, stop, run git status, and send me what it says. Do not delete the folder and start again, which is the traditional beginner move and almost never necessary.

Say the "very hard to lose" line explicitly. Fear of git is what stops people committing often, and committing often is the whole benefit.

Deliberately do not teach reset --hard today. They do not need it, and it is the one command that genuinely destroys work.
