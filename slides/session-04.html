Part one

Lists

One variable holding many values, in order.

Idea 1

A list holds things in order

Zero is the first

This is why range(5) gave you 0 to 4 last session. A list of 4 items has positions 0, 1, 2, 3. The last position is always len(list) - 1, or just -1.

Negative positions count backwards from the end, which saves you arithmetic. [-1] is "the last one" no matter how long the list is.

IndexError means you asked for a position that does not exist. Add it to your collection of recognisable errors.

The zero-based point connects back to range() from session 2. Make the link explicitly, it turns two arbitrary rules into one idea.

Idea 2

Slicing: a piece of a list

◆

Same rule as range

The end position is not included. nums[1:4] gives you three items, not four. Annoying for a week, then automatic.

One handy use: rows[:5] to peek at the first five rows of a file you just loaded, instead of printing two thousand lines into your terminal. You will do that a lot today.

rows[:5] is the practical takeaway. They will need it within the hour.

Idea 3

Growing, changing, checking

in is worth remembering

One word to ask "is this in there". You will use it constantly, and it reads like English in an if.

sorted() versus .sort()

sorted(x) hands back a new sorted list and leaves x alone. x.sort() rearranges x and returns None. Writing x = x.sort() throws your data away, and it is a genuinely common accident.

The x = x.sort() mistake is the one to show live. It connects straight back to last week: a function that changes something and returns None.

Idea 4

Looping over a list, and the accumulate pattern again

Same pattern as session 2

Set up before the loop, update inside, use after. It does not matter whether you are looping over range(10) or over two thousand rows of real data.

enumerate gives you position and value together. Reach for it when an error message says "row 47" and you want to know which row that was.

enumerate feels like a nicety now and becomes essential the first time they need to report which row of a CSV was malformed.

Part two

Dictionaries

When position is the wrong way to find something, and a name is the right way.

Idea 5

A dictionary maps names to values

A list asks "which position". A dict asks "which name".

For a row of data, names win every time. play["genre"] still makes sense in six months; play[4] does not.

The names are called keys, the things they point at are values. Keys are usually strings, and each one appears once.

KeyError means that key is not in the dictionary. Usually a typo, or a column name that is not quite what you assumed.

KeyError from a mistyped column name is the error they will hit most this week. Show it now so it is familiar later.

Idea 6

Adding, updating, and .get()

◆

When to use .get()

Use [] when a missing key means something is genuinely wrong and you want to hear about it. Use .get() with a default when missing is a normal thing that happens.

counts.get(genre, 0) + 1 is the counting pattern in one line, and you will write it in the exercise today. It means "whatever is there, or zero if nothing is, plus one".

Do not mention defaultdict or Counter yet. The .get() version makes the mechanism visible, and that is the point today. Mention Counter exists at the end if they ask.

Idea 7

Looping over a dictionary

.items() is the one you will use most. It hands you the key and the value together on every pass.

That last one looks alarming

Copy it, use it, and do not worry about lambda yet. It means "sort by the second thing in each pair". It is the standard way to turn a dictionary of counts into a top-five list, so it is worth having in your notes.

{genre:12} pads to 12 characters and {number:>5} right-aligns in 5. That is how you get columns that line up in a terminal.

Be explicit that the sorted() line is a copy-and-keep recipe, not something to derive. Permission to copy without full understanding, once, is genuinely useful here.

Part three

Files

Until now, every value has been typed into your program. Real data lives on disk.

Idea 8

open(), and why with is the way

with closes the file for you

Even if your code crashes halfway through. Always use it. An unclosed file can hold a lock on Windows and lose data you thought you wrote.

Always pass encoding="utf-8"

Without it, Python guesses based on your operating system. The guess is usually right on a Mac and wrong on Windows, and the symptom is a UnicodeDecodeError the first time somebody's name has an accent in it. Our dataset has Salon Mécanique in it, so this matters today.

The encoding point is not pedantry. It is the difference between their script working on their machine and working on anybody else's.

Idea 9 · the confusing one

Where is the file? Where am I?

■

FileNotFoundError is nearly always this

The file exists. Python is just looking somewhere else. First move: print os.getcwd() and see where you actually are.

Relative paths are counted from the folder your terminal is in, not from the file you are editing. Run the same script from a different folder and the path breaks, which is why this confuses everybody at least once.

The Path(__file__) trick means "wherever this script lives". We use it properly in session 10. For today, cd to the repo root and use relative paths.

This slide causes more confusion than the concept deserves. Have them cd around and run the same script from two places to see it break. Then agree on one habit: always run from the repo root.

Idea 10

The csv module hands you rows as dictionaries

◆

DictReader reads the header row and uses it for the keys. What you get back is exactly the shape from two slides ago: a list of dictionaries, one per row. You already know how to loop over that.

The list(...) around DictReader matters: without it you get a reader you can only walk through once, and the second loop silently does nothing. That is a real gotcha worth demonstrating.

Idea 11

Everything from a CSV arrives as text

▲

The same lesson as input()

A file has no idea what a number is. It contains characters. 4.65 in a CSV is the text "4.65" until you say float().

This is genuinely the most common source of bugs when people start working with files. When something numeric behaves strangely, print its type() first.

Session 8 is largely "pandas does this conversion for you", so make the pain vivid now. It makes read_csv feel like a gift rather than magic.

Idea 12 · the pattern of the day

Counting things into a dictionary

◆

Look at what that is: the accumulate pattern from session 2, with a dictionary instead of a single total. In session 6 you will write the same question as GROUP BY genre, and in session 8 as groupby("genre"). Same idea, three notations.

Say the "same idea, three notations" line out loud. It is the spine of sessions 4, 6 and 8, and it makes SQL and pandas feel like translations rather than new subjects.

Idea 13

Writing a CSV back out

Three arguments that matter

  • "w" means write, and it replaces the file without asking
  • newline="" stops blank lines appearing between rows on Windows
  • fieldnames sets the column order

New syntax, one line

[row for row in rows if ...] is a list comprehension: build a new list from an old one, keeping what matches. It is the same as a for loop with an append, written in one line.

Introduce the comprehension but let them write the loop version if they prefer. Being able to read one matters more than writing them right now.

The output folder needs to exist, or they get a FileNotFoundError on write. Worth mentioning: the exercise starter creates it.
