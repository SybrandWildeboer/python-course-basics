Why two pairs of brackets?

The outer pair means "select". The inner pair makes a Python list of names. Pass one name and you get one column; pass a list and you get a smaller table.

GROUP BY with several aggregates

groupby, agg, sort_values

Each line of agg is new_name=(column, what_to_do). Your session 4 homework, with its two dictionaries, in one statement: Jazz on top at 6.57.

sort_values returns a new table and leaves the old one alone, the opposite of list.sort(). To keep a result, give it a name.

No HAVING keyword is the quiet win here. In SQL, WHERE versus HAVING exists because the database needs telling when a filter happens. In pandas the order of the lines is the order things happen, so the question never comes up.

Aggregate first, then merge, then make pandas check

A CTE is a variable with a good name

Reduce both tables to one row per artist, then merge. 846.2 matches the standalone number exactly, and the grand total is 8,980.4 again.

validate= says what the relationship should be. If it is not true, the merge refuses to run, before a single wrong number exists.

validate is the habit most worth taking away from today. It turns an assumption in their head into a check the computer makes. SQL has no equivalent switch, which is one honest point in pandas' favour when a join is risky.

fillna(0) is COALESCE. The notebook also does astype(int), because a column that once held NaN is stored as decimals.

The honest version

When SQL, when pandas

Reach for SQL when
  • the data already lives in a database, especially a big one. It filters and groups where the data is, and sends back only the answer
  • other people need to run it. Analysts, engineers and dashboards all speak SQL
  • the question is a straightforward filter, group and join
Reach for pandas when
  • the data is a file: a CSV, a spreadsheet, a download
  • it needs cleaning first, row by row (session 9)
  • the next step is a chart, a loop or a function (sessions 9 and 10)
  • you are exploring, keeping each step in a variable
◆

Very often, both: SQL to fetch and reduce, pd.read_sql to cross over, pandas for the rest. For a dataset this size, either works, and the right choice is often whichever your colleagues already use. Fan-out does not care which one you pick.

Resist turning this into a contest. The real-world answer is nearly always both, with the line between them drawn at "how much data has to leave the database". Pulling a hundred million rows into pandas just to count them is the classic mistake.
