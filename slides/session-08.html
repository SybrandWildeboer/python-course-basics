Installing a package

Where does it come from?

PyPI, the Python Package Index: a public library of code other people wrote. pip downloads from it and installs into your Python.

This is the thing that makes Python worth learning. Somebody has already written the fiddly part of almost any job you have, and pandas is the most useful example of that in data work.

▲

Right now you are installing into the Python for your whole machine, which is fine for learning and becomes a problem once you have two projects wanting different versions. Session 10 fixes that properly with virtual environments.

On some systems pip is pip3. If pip install fails with a permissions or "externally managed environment" error, python3 -m pip install --user pandas is the usual way through, and it is a good preview of why venvs exist.

Basics

Selecting columns and rows

Series and DataFrame

One column on its own is a Series. Two or more is a DataFrame. That is why the double brackets: the inner pair is a list of the columns you want.

.loc is label based

Rows by index label, columns by name. And unlike everything else in Python, .loc[0:2] includes row 2. It is the one place slicing is inclusive, and it catches everybody once.

There is also .iloc, which is purely positional and exclusive at the end. Mention it, use .loc.

Do not teach the full loc/iloc matrix. .loc plus boolean filtering covers almost everything they will need this year.

The one with the sharp edge

Filtering rows

■

& and |, never and / or

Python's and wants one true-or-false value. Here each side is 2,183 of them, so pandas refuses. The message, "the truth value of a Series is ambiguous", means exactly this.

▲

And bracket every condition. & binds tighter than >, so without the brackets pandas reads it in the wrong order and the error is baffling.

These two mistakes account for a good half of pandas frustration in the first month. Have them make both errors on purpose now and read the messages.

groupby: the same idea, again

◆

Read groupby("genre")["minutes_played"].agg([...]) left to right as a sentence: split by genre, take the minutes column, work these out for each group. That is exactly what SQL's GROUP BY does, and the named form at the bottom is the closest match to AS.

The thing that confuses everybody

After a groupby, your key is the index

The grouping key moves out of the columns and becomes the row labels. Everything that then treats it as a column fails, including plotting and writing to CSV in the shape you expected.

reset_index() pushes the index back into a proper column and numbers the rows again. Reach for it whenever a groupby result is awkward to work with, and it will usually be the answer.

This is the single biggest source of pandas confusion for beginners. Show the KeyError, then the fix, and tell them reset_index() is the reflex.

Fan-out is not a SQL problem

■

Identical numbers to session 7, because it is the same arithmetic. Nothing about it was specific to SQL.

pandas has a seatbelt, though

validate= makes you state the shape you expect, and complains when you are wrong. Get in the habit: it turns a silent wrong answer into an error message.

The honest answer

So which should you use?

Reach for SQL when
  • the data already lives in a database
  • you want an answer, not a program
  • the data is bigger than your memory
  • somebody else needs to run the same query
  • filtering or joining before you pull it down saves real time
Reach for pandas when
  • you need to clean or reshape, not just select
  • you want a chart at the end
  • the logic is awkward or impossible in SQL
  • it is part of a larger Python program
  • you are exploring and want to iterate quickly
◆

In practice, both, in that order

pd.read_sql exists precisely for this. Let the database do the filtering and joining, where it is fast and the data lives; hand pandas a smaller, tidier table to clean, reshape and chart. That is what session 10's pipeline does.

◆

No dogma. People get strangely tribal about this, and it is a choice of tool, not of team.

Resist any temptation to declare a winner. The useful answer is "both, and here is how they fit together", which is also what they will see in any real workplace.

On SettingWithCopyWarning

It means "you may have changed a copy rather than the real thing, and I cannot tell". It is a warning, not an error, so your code carries on and may have done nothing. Always assign with .loc and it never appears.

On inplace=True

Just do not. It saves five characters, it is no faster, it does not chain, and it makes half your lines change things invisibly. Assign the result.

Explain SettingWithCopyWarning once, calmly, and give them the .loc habit rather than a full explanation of views and copies. The habit prevents it entirely.
