Teaching the course

How a session runs, what to check before each one, the tools that keep the materials honest, and how to pace it for a learner who goes fast. Each session's own run sheet has the detail; this page is the part that is the same every week.

12 sessions of 2 hours one to one 2 to 4 hours homework a week a run sheet per session

How a session runs

The same shape every week

  • 0:00, homework review, 10 to 15 minutes. They run their homework, not you, and you start with what broke. It is also the retention check: you see straight away what stuck from last week.
  • Teaching, in two blocks around a ten-minute break near the hour. The run sheet says which slides go in which block, and which block to protect.
  • The live exercise, with them driving. Their keyboard, their screen. You ask questions; you do not type.
  • The last 5 to 10 minutes: homework briefing. From session 6, also commit and push.

Homework is 2 to 4 hours and meant to be a bit too hard. On Saturday they send one line, Homework done or Homework not done. A "not done" is information, not failure: it tells you what to start the next session with. Answers are in homework/solutions/, for after the Saturday line.

Each session's README.md is its run sheet: timings, the slides that carry the session, the files, what to watch out for, and a definition of done. Speaker notes are in the deck: press n. Press o for a grid of every slide.

Before every session

Twenty minutes, the day before

  1. Read the session's run sheet, especially The slides that matter and Watch out for. Note which block you will protect if time runs short.
  2. Click through the deck with the speaker notes open.
  3. Run the session's notebooks, so nothing surprises you live (Windows; on macOS type python3): 
    python tools/nbtool.py run sessions/session-07
  4. For a SQL session, run its queries too: 
    python tools/check_sql.py sessions/session-07
  5. Look at their Saturday line, and their pushed homework once they have a repo (from session 5), so the review starts with what they actually did.
  6. Do the session's own checklist, in the table below.

If you change the materials after session 5, the learner gets the change with git pull course main: in session 5 the course remote is renamed to course, and origin becomes their own repo.

The checks in tools/

Run these after you change anything

They are how the course stays true: a query on a slide that does not run, or a number that no longer matches, is worse than no query at all. From the repository folder (python3 on macOS):

python tools/nbtool.py check      # notebooks are valid JSON, compile, carry no saved output
python tools/nbtool.py run        # every solved and walkthrough notebook runs top to bottom
python tools/check_sql.py         # every .sql file runs, with the row counts it claims
python tools/check_slides.py      # every slide fits at 1280x720 and has speaker notes

Each takes a folder or session to narrow it down, as in python tools/nbtool.py run sessions/session-10 or python tools/check_slides.py 10.

ToolWhat it does
nbtool.pycheck is fast and needs nothing installed. run executes every notebook from the repository folder and skips the -exercise and -homework starters, which are meant to be full of TODOs. strip removes saved output before a commit. convert turns a percent-format .py into a notebook.
check_sql.pyRuns every statement in every .sql file against a throwaway copy of data/music.db, so the real database is never touched. A -- expect: N rows comment pins the row count of the statement after it.
check_slides.pyOpens each deck in a headless browser and reports content cut off, code blocks that scroll sideways, slides with no notes, and JavaScript errors. --shots saves a PNG per slide to tools/.shots/, which git ignores.

The extras they need

check and check_sql.py use only the standard library. nbtool.py run and check_slides.py need:

python -m pip install playwright nbformat nbclient ipykernel
python -m playwright install chromium

The session 12 tests run with pytest, one folder at a time: python -m pytest sessions/session-12/solutions (35 tests). Never run it with no folder from the repository root: it collects the exercise starter, which fails on purpose.

The stretch notebooks

For when a session runs early, sessions 3 to 12

Every session from 3 on has a -stretch-exercise.ipynb and a -stretch-solved.ipynb. Six or seven exercises that get harder as they go, each adding one idea the main session did not have time for. Use as many as the time allows; nobody needs to finish one. Each run sheet's If there is time left section lists them and says which one to talk through rather than just check.

  • Session 5's stretch is instructions only: the work happens in the terminal, in a throwaway git-playground repo.
  • Session 6 and 7 stretches have their queries in solutions/stretch.sql, with row counts pinned, so check_sql.py keeps the notebook's numbers true.
  • Session 8: if part one runs early, spend the time on the side-by-side block, not the stretch. That block is the session.
  • Session 11's stretch is the Spotify route on a practice export. It is the head start for anyone whose project will use the real one.
  • Session 12 rarely has time left. Its stretch is written to work alone in the week after.

The full list of stretch notebooks is on the sessions page.

Pacing a fast learner

Go deeper before you go faster

  • Keep the two-hour slots. Finishing early is not a reason to end early, or to start the next session. The time between sessions, with the homework, is where it sets.
  • Check retention, not speed. Fast in the session can still mean gone by next week. The homework review is the test: they run it and explain it. Ask for one thing from two sessions back without notes, such as return versus print, or why a join made a total bigger. If it is not there, that is the next ten minutes.
  • Stretch first. When a session runs early, reach for its stretch notebook before pulling material forward. It stays on the same idea and goes further, which is what builds confidence that lasts.
  • If you must save a week, two merges are possible: 3 with 4, and 6 with 7. In each pair the second session builds directly on the first with no new setup. The cost is a homework week, so only merge when the retention checks say the first session has stuck. When merging 6 and 7, follow session 7's own advice: cut views and the subquery variations, and never the fan-out block, which needs the most practice of anything in the course.
  • Do not compress sessions 10 to 12. The virtual environment has to work on their machine before session 11, and the project needs its two weeks before session 12.
