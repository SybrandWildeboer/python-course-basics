Teaching the course

How a session runs, what to check before each one, what to watch out for, the tools that keep the materials honest, and how to pace it for a learner who goes fast. Each session's own run sheet has the detail; this page is the part that is the same every week.

12 sessions of 2 hours one to one 2 to 4 hours homework a week a run sheet per session

How a session runs

The same shape every week

  • 0:00, homework review, 10 to 15 minutes. They run their homework, not you, and you start with what broke. It is also the retention check: you see straight away what stuck from last week.
  • Teaching, in two blocks around a ten-minute break near the hour. The run sheet says which slides go in which block, and which block to protect.
  • The live exercise, with them driving. Their keyboard, their screen. You ask questions; you do not type.
  • The last 5 to 10 minutes: homework briefing. From session 6, also commit and push.

Homework is 2 to 4 hours and meant to be a bit too hard. On Saturday they send one line, Homework done or Homework not done. A "not done" is information, not failure: it tells you what to start the next session with. Answers are in homework/solutions/, for after the Saturday line.

Each session's README.md is its run sheet: timings, the slides that carry the session, the files, what to watch out for, and a definition of done. Speaker notes are in the deck: press n. Press o for a grid of every slide.

Tone

The decks are deliberately warm and deliberately direct. Two rules are worth keeping if you edit anything:

  • No em dashes, anywhere. A house style choice. None of the slides, pages or run sheets use one.
  • Encouragement is specific. "Your clean() docstring records the decisions, which most professionals do not bother with" is worth ten times "good job".

Before every session

Twenty minutes, the day before

  1. Read the session's run sheet, especially The slides that matter and Watch out for. Note which block you will protect if time runs short.
  2. Click through the deck with the speaker notes open.
  3. Run the session's notebooks, so nothing surprises you live (Windows; on macOS type python3): 
    python tools/nbtool.py run sessions/session-07
  4. For a SQL session, run its queries too: 
    python tools/check_sql.py sessions/session-07
  5. Look at their Saturday line, and their pushed homework once they have a repo (from session 5), so the review starts with what they actually did.
  6. Do the session's own checklist, in the table below.

If you change the materials after session 5, the learner gets the change with git pull course main: in session 5 the course remote is renamed to course, and origin becomes their own repo.

The checks in tools/

Run these after you change anything

They are how the course stays true: a query on a slide that does not run, or a number that no longer matches, is worse than no query at all. From the repository folder (python3 on macOS):

python tools/nbtool.py check      # notebooks are valid JSON, compile, carry no saved output
python tools/nbtool.py run        # every solved and walkthrough notebook runs top to bottom
python tools/check_sql.py         # every .sql file runs, with the row counts it claims
python tools/check_slides.py      # every slide fits at 1280x720 and has speaker notes

Each takes a folder or session to narrow it down, as in python tools/nbtool.py run sessions/session-10 or python tools/check_slides.py 10.

ToolWhat it does
nbtool.pycheck is fast and needs nothing installed. run executes every notebook from the repository folder and skips the -exercise and -homework starters, which are meant to be full of TODOs. strip removes saved output before a commit. convert turns a percent-format .py into a notebook.
check_sql.pyRuns every statement in every .sql file against a throwaway copy of data/music.db, so the real database is never touched. A -- expect: N rows comment pins the row count of the statement after it.
check_slides.pyOpens each deck in a headless browser and reports content cut off, code blocks that scroll sideways, slides with no notes, and JavaScript errors. --shots saves a PNG per slide to tools/.shots/, which git ignores.

The extras they need

check and check_sql.py use only the standard library. nbtool.py run and check_slides.py need:

python -m pip install playwright nbformat nbclient ipykernel
python -m playwright install chromium

The session 12 tests run with pytest, one folder at a time: python -m pytest sessions/session-12/solutions (35 tests). Never run it with no folder from the repository root: it collects the exercise starter, which fails on purpose.

The stretch notebooks

For when a session runs early, sessions 3 to 12

Every session from 3 on has a -stretch-exercise.ipynb and a -stretch-solved.ipynb. Six or seven exercises that get harder as they go, each adding one idea the main session did not have time for. Use as many as the time allows; nobody needs to finish one. Each run sheet's If there is time left section lists them and says which one to talk through rather than just check.

  • Session 5's stretch is instructions only: the work happens in the terminal, in a throwaway git-playground repo.
  • Session 6 and 7 stretches have their queries in solutions/stretch.sql, with row counts pinned, so check_sql.py keeps the notebook's numbers true.
  • Session 8: if part one runs early, spend the time on the side-by-side block, not the stretch. That block is the session.
  • Session 11's stretch is the Spotify route on a practice export. It is the head start for anyone whose project will use the real one.
  • Session 12 rarely has time left. Its stretch is written to work alone in the week after.

The full list of stretch notebooks is on the sessions page.

Pacing a fast learner

Go deeper before you go faster

  • Keep the two-hour slots. Finishing early is not a reason to end early, or to start the next session. The time between sessions, with the homework, is where it sets.
  • Check retention, not speed. Fast in the session can still mean gone by next week. The homework review is the test: they run it and explain it. Ask for one thing from two sessions back without notes, such as return versus print, or why a join made a total bigger. If it is not there, that is the next ten minutes.
  • Stretch first. When a session runs early, reach for its stretch notebook before pulling material forward. It stays on the same idea and goes further, which is what builds confidence that lasts.
  • If you must save a week, two merges are possible: 3 with 4, and 6 with 7. In each pair the second session builds directly on the first with no new setup. The cost is a homework week, so only merge when the retention checks say the first session has stuck. When merging 6 and 7, follow session 7's own advice: cut views and the subquery variations, and never the fan-out block, which needs the most practice of anything in the course.
  • Do not compress sessions 10 to 12. The virtual environment has to work on their machine before session 11, and the project needs its two weeks before session 12.

What not to teach

Deliberately left out, because they cost more than they give at this stage

  • git reset --hard. It really destroys work, and git restore and git revert cover what they need. If they find it online, say so.
  • global. If they find it, say it exists, that it is almost always the wrong tool, and steer back to parameters and return values.
  • Mutable default arguments. A real Python trap, and completely wrong for session 3. The session 3 notes say not to mention them.
  • inplace=True in pandas. Tell them not to, and why: it returns None, so nothing chains after it. Session 8 has a slide on it.
  • Classes. Nothing in the course needs one, and they are a session of their own.
  • Views and copies in pandas. Teach the habits instead: .loc to change the original, .copy() after a filter for a new table. Session 8's first notebook sets the warning off once, on purpose.

If they want to use their own data

Better, if they care about it, and real work for you

The whole course runs on the listening log, and the exercises, slides and checks quote its exact numbers. Swapping it for the learner's own data means translating every exercise yourself, so weigh that against how much the motivation is worth.

  • What it needs: a few thousand rows at most, at least one date column, one numeric column, a few categorical columns, and something that can become a second, related table for the joins in session 7.
  • When to decide: before session 6, when the database appears.
  • The cheap route: keep the course data for sessions 1 to 10, and let their own data in at session 11, where the project is built for it. It goes in project/data/, which git ignores apart from its README.

Watch out for, all in one place

For when a question arrives mid-week

Every session's run sheet ends with a Watch out for list, with more context. This is all of them, grouped by topic, so you can find the likely cause fast. The session is in brackets.

Setup and environment

  • Windows PATH. "Add python.exe to PATH" is unticked by default. Close every terminal and open a new one; if it still fails, re-run the installer, Modify, tick the box. (1)
  • python versus python3. On Windows it is python, and python3 may open the Microsoft Store. On a Mac it is python3 until a venv is active. Agree it in session 1. (1, 10)
  • Not saving before running. Python runs the file on disk. VS Code puts a dot on the tab of an unsaved file. (1)
  • Smart quotes pasted from a chat app. When a SyntaxError looks impossible, retype the quotes. (1)
  • Opening a file instead of the folder in VS Code, so the terminal starts in the wrong place. (1)
  • The install running long. Normal. Drop material rather than rushing the second half. (1)
  • The notebook kernel is a different Python. No module named 'pandas' in a notebook. (8, 10)
  • PowerShell refusing to activate. Set-ExecutionPolicy -Scope CurrentUser RemoteSigned, once. (10)
  • Forgetting to activate. No (.venv) at the start of the prompt means the venv is not active, not that pandas is missing. (10)
  • Committing .venv/. The root .gitignore covers it; git status after creating it is the proof. (10)

Python

  • = versus ==, missing colons, and indentation, where mixed tabs and spaces is the nasty version. (2)
  • range(1, 10) not including 10. Say it, show it, let them be annoyed. (2)
  • total = 0 inside the loop. Let them hit it, then ask what is resetting. (2)
  • Deep nesting in the guessing game. Let them finish, then flatten it together. (2)
  • Printing instead of returning. Ask for one summary line with all four numbers and let the requirement force the change. (3, and again in 10)
  • Defining a function and never calling it, or calling it without brackets. (3)
  • A variable from inside a function, used outside it. The NameError is the lesson. (3)
  • A return inside an if with no other path: None for some inputs. (3)
  • x = x.sort() throwing the list away. (4)

Files

  • FileNotFoundError from a relative path. First move, every time: print os.getcwd(). Run from the repo root. (4)
  • No list() around DictReader. The second loop silently does nothing. (4)
  • Everything from a CSV is text. float() before arithmetic. (4)
  • A mistyped column name. rows[0].keys(). (4)
  • No encoding="utf-8". On Windows, Salon Mécanique comes out as Salon MÃ©canique, with no error. (4)
  • Writing to output/ before it exists. os.makedirs("output", exist_ok=True). (4)

Notebooks

  • The run-order trap. Cells remember what ran, not what is on screen. Restart and Run All is the fix and the standard. (1, 10)
  • Notebooks committed with saved output. python tools/nbtool.py check, then strip. (5)
  • __file__ in a notebook. A NameError, which is why every notebook starts with the walk-up cell. (10)
  • Anything interactive is a script. The guessing game and the menu use input(), and have no notebook. (2, 3)

Git

  • user.name and user.email not set. The most common first-commit failure. Do it first. (5)
  • Committing junk. Read .gitignore together: output/ is why the session 4 CSVs never showed up. (5)
  • Messages like "stuff". Do not lecture; the homework has them read their own messages back. (5)
  • Fear of breaking things. Say more than once that committed work is very hard to lose. (5)
  • Merge conflicts. Out of scope in session 5. If one happens, resolve it together, calmly. (5)
  • git add . with private data in project/data/. Before the first project commit. (11)

SQL

  • == instead of =. A Python habit. SQLite quietly accepts ==, so there is no error to learn from; most other databases reject it. Correct it anyway. (6)
  • Double quotes around text. They mean a column name. SQLite treats "phone" as text only because no column has that name; WHERE device = "device" matches all 2183 rows. Inside a Python string the double quotes end the string, a SyntaxError. (6)
  • = NULL. Runs, returns nothing, warns nobody. (6)
  • Ungrouped columns in the SELECT. SQLite permits it: SELECT artist_name, COUNT(*) FROM artists returns one arbitrary name next to 40. (6)
  • A count in the WHERE. misuse of aggregate: COUNT(). The execution-order slide explains why HAVING. (6)
  • Integer division. 19 / 179 is 0; 100.0 * first. Homework question 9. (6)
  • LIMIT without ORDER BY. Arbitrary rows that happen to look stable in SQLite. (6)
  • Ambiguous column names after a join. Alias and qualify. (7)
  • COUNT(*) after a LEFT JOIN says 1 for a row with no match, so "never played" becomes "played once". (7)
  • Fan-out. After any join, compare the row count with the count before. (7, and 8 in pandas)
  • Reaching for DISTINCT. SUM(DISTINCT) gives Fjord & Flint 680.6 minutes, not 846.2: a second wrong answer. (7)
  • Assuming the keys match. True here, rarely in real data. (7)

The real error messages, with fixes, are on the troubleshooting page.

pandas

  • and and or in a filter. "The truth value of a Series is ambiguous". And brackets missing around an | inside an &: no error, wrong number. (8)
  • = instead of == in a mask, a SyntaxError, and plays.shape(), a TypeError. (8)
  • Single versus double brackets. A column or a one-column table. (8)
  • Not assigning the result. sort_values and .str.lower() return something new and leave the original alone. (8, 9)
  • merge is an inner join by default. Why eleven countries vanish in part 2 of the exercise. (8)
  • size versus count, which is COUNT(*) versus COUNT(column) again. (8)
  • formed_year as 2014.0. A column with a NaN in it is stored as decimals. (8)
  • SettingWithCopyWarning, inplace=True and .loc[0:2] giving three rows. (8)
  • errors="coerce" first, and trusting format="mixed". Both hide failures. Count the missing values before and after. (9)
  • value_counts() hiding missing values. Without dropna=False, 70 blank devices vanish. (9)
  • A bare dropna(), which drops a row for a gap in any column, and fillna(0), which drags the average from 4.121 to 3.943. (9)

Charts

  • plt.savefig after plt.show() saves a blank PNG in a script. Save first. (9)
  • A title that claims more than the data shows, and an axis that exaggerates a small difference. Session 9's chart notebook has both. (9)
  • A stale chart in the presentation. Run the pipeline first. (12)

The pipeline and the project

  • parents[3] off by one. parents[0] is the folder the file is in. Print ROOT first. (10)
  • "My data file is not in git status." On purpose: project/data/ is ignored apart from its README. (10)
  • The project that will not stop growing, and data they do not have yet. Every "and also" goes on the could list; the first run uses data that is on the laptop today. (11)
  • A file that reads without an error, but wrongly. Dutch Excel saves CSVs with ; and decimal commas. Excel files need openpyxl, which is not in requirements.txt. (11)
  • save_csv dropping the labels. It writes with index=False; end analyse with .reset_index(). (11)
  • Changing everything at once, and underestimating. One step, one run. (11)
  • One giant commit, so there is no history to review. (12)
  • A bare except:, or a try around everything. In most projects only the load in main() and text that may not be a number need one. (12)
  • pytest trouble. python -m pytest, with a folder named. Never a file called statistics.py. (12)
