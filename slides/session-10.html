Part one · 25 minutes

Virtual environments

The thing you have been quietly getting away with not having.

The problem

Why your pip install is a problem waiting to happen

When you ran pip install pandas in session 8, it went into the Python for your whole machine. Every project you ever write shares it.

That is fine until it is not. Project A needs pandas 1.5 and project B needs pandas 3.0. You upgrade for B, and A silently breaks. Or you hand your project to somebody and they have no idea which packages it needs, because the answer is "whatever happened to be on your laptop".

A virtual environment is a folder

It holds its own copy of Python and its own packages, just for this project. Nothing in it can affect anything else on your machine.

And it answers the other question too

Because the project's packages live in one place, you can write down exactly what they are. That list, requirements.txt, is what makes your project runnable by somebody else, including future you on a new laptop.

The "hand it to somebody" framing works better than the version-conflict one, because they have not hit a version conflict yet but they are about to hand in a project.

Do it now

Four commands, and one you will forget

▲

Step 2 is the one you will forget

Activating is per terminal, every time. Forget it and pip install goes to your machine again, or your script cannot find pandas. The tell: your prompt shows (.venv) when it is active.

.venv/ goes in .gitignore

It is hundreds of files and thousands of lines of somebody else's code, and it is specific to your operating system. Commit requirements.txt instead: it is one small text file that lets anybody rebuild the folder exactly.

In VS Code, once .venv exists it will usually offer to use it, and the notebook kernel picker will list it. Show them that, because otherwise the notebook and the terminal end up using different Pythons, which is maddening to debug.

Layout

A project that somebody else can pick up

The idea behind it

  • data/ is input, and you never edit it by hand
  • src/ is what you wrote
  • output/ is what the code made, and can always be deleted and remade
  • notebooks/ is where you worked it out

The test that it is right

Delete output/ and run the script. If everything comes back, the structure is honest. If something does not, you had a file you could not regenerate, and you did not know it.

That is your homework, and it catches real mistakes.

The delete-and-rerun test is the thing to emphasise. It is how you find out that your notebook quietly wrote a file your script depends on.

Layout

The README.md is the front door

Four things, and no more

  1. The question, in one or two sentences, at the very top
  2. How to run it, as commands somebody can copy
  3. What it produces
  4. What you found

The question goes first because it is the thing a reader needs before anything else makes sense. Writing it down also stops the project drifting: if a new idea does not serve the sentence at the top, it is a different project.

You write this one in session 11, before you write any analysis code. It takes ten minutes and it is the most useful ten minutes of the project.

The "if it does not serve the sentence at the top it is a different project" line is the scope-creep defence for session 11. Plant it here.

Part two · the rest of the session

The pipeline

Notebook to script. You type, I watch.

The move

When a notebook should become a script

A notebook is right when
  • you are still working out what the question is
  • you want to see each step
  • the output is the point: a chart, a table, a write-up
  • you will read it again more than you run it
Time to make it a script when
  • you have run the same cells in the same order three times
  • you want it to run without you
  • somebody else needs to run it
  • you find yourself scrolling up to re-run a cell you already know works
◆

It is not either/or, and the pairing is the point

Explore in the notebook, then move the settled parts into a script and import them back into the notebook. The script becomes the thing that runs; the notebook becomes the place you look at what it produced. Nothing gets copied twice.

◆

Remember session 9: you copied clean_plays() from one notebook into another, because notebooks do not share state. That itch is exactly what this solves.

"You copied the function between notebooks" is a concrete pain they felt last week. Point at it; it makes the move feel necessary rather than tidy.

Structure

Four steps, four functions

This is the shape of almost every data script anybody writes, under many different names. Naming the four steps is most of the value.

Two habits that prevent whole classes of bug

Constants at the top, paths from the file

Path(__file__) means "where this script lives"

So the script works from any folder. That is the permanent fix for every FileNotFoundError you hit in session 4, and it is why you no longer need the "run it from the repo root" rule.

Everything adjustable in one place

Filenames, thresholds, column lists. When something needs changing there is exactly one place to look, and you never go hunting through the middle of a function for a hardcoded number.

Never a path like /Users/sam/Documents/project/data.csv. It works on precisely one machine, which is yours, until you rename the folder.

The hardcoded absolute path is the single most common thing that stops a beginner's project running on anybody else's machine. Name it explicitly.

One piece of syntax

if __name__ == "__main__":

Read it as: "the part that runs when you run this file"

Run it directly and main() happens. Import it from a notebook and it does not, so you get the functions without the whole pipeline firing off.

That is the notebook and script working together: the script owns the logic, the notebook borrows it to look at things.

Keep the explanation light, exactly as the outline says. "The part that runs when you run this file" is enough, and the import demo makes the reason concrete.

Small, and it pays for itself

Print progress, so you can see where it failed

silent

Something broke. Was the data loaded? Did the cleaning run? No idea.

chatty

Loading and cleaning were fine, and 2,183 rows survived. The problem is in the analysis.

◆

Print the row count after each step. It costs four lines and it tells you both where a crash happened and whether a step quietly threw away half your data, which is the session 9 lesson arriving in a new place.

Real projects use the logging module for this. Do not introduce it: print is completely fine at this scale, and one more concept today would not fit.

The shape of it

The whole pipeline, from a distance

Read top to bottom and you learn the project

The docstring says what it does. The constants say what it touches. The function names say the steps, in order. Nobody has to read the bodies to understand the shape.

Every function does one thing

And is named after what it gives you. That is session 3, arriving where it pays off: clean() can be tested on its own, and write_chart() does not care where the numbers came from.

The warning sign to watch for: a function that loads, calculates and writes a file. When you cannot name a function after one thing, it is doing more than one.

Show the real file next to this outline. The whole point of the naming and ordering is that a stranger can follow it, and they are about to become the stranger for their own project in two weeks.

Practical

Debugging a script, when there are no cells

1. Read the traceback from the bottom

Same habit as session 2. The last line says what went wrong; the line above it says where. In a script the middle now matters too: it shows which function called which, so you can see the route in.

2. Print the shape between steps

Which you already do, because main() reports row counts. Half of "why is this wrong" is answered by noticing that a step dropped 1,800 rows.

3. Pull the broken function into a notebook

This is the one worth having. Import it, call it with real data, and poke at the result interactively. No print statements, no guessing.

The script keeps the logic; the notebook is the workbench. This is why the four steps are separate functions, and why none of them print.

This slide is the payoff for the whole structure. Demonstrate it live: break one function on purpose, then debug it from a notebook.

Reference · you will want this in two weeks

What a finished project looks like

  • README.md with the question at the top and the commands to run it
  • requirements.txt, and a .venv/ that is gitignored
  • One command runs the whole thing
  • Delete output/, run it, everything comes back
  • No absolute paths anywhere
  • Constants at the top, not buried in functions
  • Each function does one thing and is named after it
  • The functions return; only main() prints
  • Every chart has a title stating the finding, and labelled axes
  • A written conclusion that says what you cannot conclude
◆
