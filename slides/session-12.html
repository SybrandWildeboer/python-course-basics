Afterwards

The four questions any reviewer asks

  1. How do you know the number is right? Which number was confirmed a second way, and how?

  2. What did cleaning remove? Would the answer change if it had not?

  3. What is the smallest change to the data that would change your conclusion?

  4. Who else could run this, and what would they need?

"I do not know yet" is a good answer

Followed by how you would find out. Making up a confident answer on the spot is the habit to avoid, in this room and every other.

Then one thing to keep

Before any criticism: the one decision in the project that was clearly right. Feedback that only lists problems teaches people to avoid feedback.

Question 3 is the hardest and the most valuable. If the conclusion rests on 12 plays in one month, say so kindly: the honest version of the finding is smaller and still interesting.

Say the thing to keep first, and mean it. Then at most two improvements.

Idea 1

Some errors are not bugs

Your session 3 functions, unchanged

Nothing is wrong with average. It was asked for the average of nothing, and there is no such number.

Predictable

You can say in advance when each of these happens and which error it will be. That is the test for whether try is the right tool.

A NameError from a typo is not predictable. It is a bug. You fix it, you do not catch it.

All four errors are ones they have met: ZeroDivisionError and IndexError in session 2 homework, ValueError from input() in sessions 1 and 3, FileNotFoundError in session 4. Today is not new errors, it is a new response to old ones.

Idea 2

try / except: say what to do instead

How it runs

Python runs the try block. If that named error happens, it jumps to except. If nothing goes wrong, except is skipped.

The session 3 menu, fixed

The homework solution checked numbers with .lstrip("-").replace(".", "", 1).isdigit() and called it "not elegant". It also refused "1e3". Asking float() itself is the only check that always agrees with float().

For the empty list, an if len(numbers) == 0 is clearer. try earns its place when checking first is awkward: text, and files.

Run to_number over the messy file's minutes column in the notebook: 2,033 numbers and 190 that are not, which are 96 like "4.2 min" and 94 empty strings. Returning None is a decision, not a fix; that is session 9's lesson again.

Idea 3 · the rule

Name the error. Never a bare except:

catches everything
catches the one you expected
■

The bare except turned a typo into "the list was empty"

You would now spend an hour looking for a data problem that does not exist. Catch the one error you expected, by name, and let everything else crash. An unexpected crash is information. A swallowed one is a lie you find later.

except Exception is the same thing in a more respectable coat. They will see it in other people's code. Treat it as a question to ask in review, not a pattern to copy.

Idea 4 · the bad file path

Catch it in the outer layer

The empty list lies

Every number downstream becomes a confident zero, or a crash three functions later that has nothing to do with files. It is the same lie as returning 0 for the average of nothing.

The session 3 rule, extended

Functions that calculate return, and let errors travel. Only the outer layer prints, and decides what to do about errors.

raise SystemExit(message) prints the message and stops, without a traceback, because there is nothing more to learn from one.

This is exactly the bug in the practice diff from part two: load returned an empty DataFrame, and the crash came later as KeyError 'artist_name'. Connect the two out loud.

Idea 5

From assert lines to tests

Your session 3 asserts, each in a function

Named as a sentence that says what should be true, starting with test_, in a file whose name starts with test_.

pytest.raises

"Inside this block I expect a ZeroDivisionError." The test passes only if the error happens. That pins down a decision you made on purpose.

The functions moved to statistics_functions.py, with no prints and no asserts at the bottom, because importing a file runs it.

Three problems with asserts at the bottom of a file: they stop at the first failure, they run on every import, and nobody runs them on purpose. Tests fix all three.

The notebook builds a ten-line test runner first, so pytest arrives as "this, with a nicer report" rather than as magic.

Idea 6 · do it now

python -m pytest, then break something

Each dot is a passing test. Not installed? With the project's virtual environment active: python -m pip install pytest

Output trimmed to the lines that matter; the full report also prints the platform and rootdir. The second failure is the one to dwell on: with best = 0, highest([]) stops crashing and quietly answers 0. The test for the awkward case caught a lie the first test could not see.

python -m pytest rather than pytest, for the same reason as python -m pip: it is the pytest of the Python you are actually using.

Idea 7 · in project/

What to test, and where it goes

Starter: homework/test_pipeline_starter.py. Worked example: homework/solutions/.

Test the calculating functions

Clean and analyse, where the decisions live. On three or four rows you build by hand, never on the whole file. If you need a calculator to know the answer, the test is too big.

The awkward cases

Empty, one item, negatives, zero, missing. The ordinary case nearly always works.

You can only test what returns

A function that prints its answer cannot be checked by a test at all. The session 3 rule pays out one more time.

Install into the project venv, add pytest to project/requirements.txt, put the test file next to pipeline.py, run python -m pytest from inside project/.

The habit that matters most

Know roughly what the answer should be before you run the code, and check it a second way afterwards. Tools change every few years. That habit has not changed in fifty, and it is what separates analysis people can trust from analysis that only looks right.

Go through the list slowly and let them notice how far it goes. Twelve sessions ago the first item was "print a line".
