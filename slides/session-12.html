Point five is the interesting one

What you abandoned, and why, tells me more about how you are thinking than the finished code does. Deciding not to do something is a skill, not a failure.

If something does not work, show it anyway and say so. A project with an honest "this bit is broken and here is what I think is wrong" is stronger than one that quietly avoids the subject.

Do not interrupt. Write things down: naming, repetition, functions doing too much, charts that over-claim, anything that would break if the data changed.

0:25 to 1:00

Code review

A real review, the way it happens at work. Not an inspection.

Setting expectations

What a code review actually is

What it is
  • Two people reading code together
  • Questions more than statements
  • Finding the two or three things worth changing
  • About the code, never about you
What it is not
  • A list of everything imperfect
  • A test with a score
  • Me rewriting it the way I would have
  • An argument about style
◆

You should push back. If I suggest something and you have a reason for what you did, say so: half the time the reason is good and I did not know it. A review where one person just accepts everything is not a review, it is a lecture with extra steps.

Mean the push-back invitation. If they defend a decision well, say so out loud; it is the most useful thing that can happen today.

The angles

Five questions we will ask of your code

QuestionWhat we are looking for
Is it readable? Would you understand this in six months? Names that say what things are. A structure you can follow top to bottom without holding much in your head
Does each function do one thing? If you cannot name it after one thing, it is more than one. Watch for load-and-clean-and-save
What happens if the data changes slightly? An extra column, a new category, a missing month, twice as many rows. What breaks, and would you notice?
Where is the repetition? The same three lines twice usually wants to be a function with a parameter
Does the conclusion follow from the analysis? The most important one. Does the code actually compute what the README claims?
◆

That last question is the one professionals get wrong most often, and it has nothing to do with Python. A correct calculation of the wrong thing is the most expensive bug there is, because everything about it looks fine.

Work through the code with these five, in this order. "What if the data changed" is the one that most reliably finds real fragility: hardcoded column lists, assumed date ranges, a groupby that silently drops a new category.

Live

Pick two or three things and fix them now

Why live, and why only two or three

Because a list of improvements you take away is a list you will not do. Two changes made now, with the code in front of you, are worth more than ten written down.

Good candidates

  • a name that is not quite right
  • a function doing two things, split in half
  • a repeated block turned into a parameter
  • a chart title that claims more than the data shows
  • a hardcoded value lifted to the top of the file

And the final commit

Finish with the changes committed and pushed. The last thing in your history should be a real improvement made in a review, which is exactly how professional work goes.

Then run the delete-and-rerun test one last time. If output/ regenerates after the edits, nothing got broken.

◆

Say clearly what you did well, and be specific about it. Twelve weeks ago you had never written a line of Python. That is worth more than a moment's acknowledgement.

Do the praise properly and specifically. Vague encouragement is forgettable; "your clean() docstring records the decisions, which most professionals do not bother with" is not.

What is next

A map, not a syllabus. You do not need most of this, and it helps to know it is there.

Closest to what you know

Five things that plug straight into what you can already do

Error handling: try / except

The thing you kept bumping into: what should happen when the file is missing or the input is nonsense? You have wanted this since session 3.

Testing: pytest

Code that checks your code. You have already done the honest version with assert in session 3; pytest is that, with a runner and better messages.

APIs and requests

Getting data from the internet instead of a file. Usually about fifteen lines, and it turns "the data I have" into "the data that exists".

Automation

Making a script run itself: cron on Mac and Linux, Task Scheduler on Windows, GitHub Actions in the cloud. This is where the "automate the annoying thing" idea actually pays off.

More of the notebook and script split

You already have this. The next step is noticing, over time, which of your habits belong in which shape.

If you only do one: try / except. It is small, it is immediately useful, and it makes everything you have already written more robust.

try/except is the right recommendation here because they have hit the need for it repeatedly and it is a single afternoon of learning.

The social half of git

Git, with other people in it

Everything you learned in session 5 was git on your own. The other half is what makes it worth the trouble.

  • Forks and pull requests: propose a change to somebody else's project without needing permission first
  • Code review on a pull request: what we did today, in writing, asynchronously
  • Merge conflicts: what happens when two people change the same lines. Survivable, and less frightening once you have done one
  • Branch per change: the habit that makes all of the above work

Day to day, on a team

Pull the latest main. Branch. Make a small change. Push, open a pull request, get it reviewed, merge. Repeat. That loop is most of what software work looks like from the outside.

A good way to practise

Fix a typo in the documentation of a project you use, as a pull request. Genuinely useful, completely safe, and it teaches the whole mechanism in one go.

The documentation-typo pull request is a real recommendation. It is the least intimidating way into the workflow and maintainers are usually delighted.

If the data grows

SQL beyond SQLite

PostgreSQL, and the server model

SQLite is a file. Postgres is a program that many people and programs talk to at once. Same SQL, plus users, permissions and backups.

This is what "the database" means at most workplaces.

Indexes, and why queries get slow

An index is the difference between reading every row and jumping straight to the right ones. It is why one query takes 20ms and a similar-looking one takes 40 seconds.

Learn EXPLAIN when you first meet a slow query.

Window functions

The thing that was missing in session 8's awkward question: a running total, a rank within a group, a comparison to the previous row.

The biggest single upgrade to your SQL from here.

◆

Everything you learned in sessions 6 and 7 transfers unchanged. SELECT, WHERE, GROUP BY, joins and CTEs are the same in every database, and fan-out is fan-out everywhere.

Window functions are the honest answer to "what should I learn next in SQL". They solve problems they have already hit.

Four directions

Where people usually go from here

Automation and scripting

The highest-value path if your job has repetitive work in it. Files, spreadsheets, emails, reports. Unglamorous, and it buys back hours every week for the rest of your career.

Data analysis

Deeper pandas, some statistics, and dashboards. The main thing to add is not a library: it is enough statistics to know when a difference is real, which is the question your findings.md kept running into.

Web

Streamlit turns a script into a shareable web page in an afternoon, and it is the fastest way to make your work visible to somebody else. Flask or FastAPI for real backends, which is a bigger commitment.

Machine learning

Honestly: it is mostly data work with a model at the end. The pandas and SQL you have are 80% of the job, and the cleaning judgement from session 9 matters more than the algorithm. Do not start here because it sounds exciting.

Be honest about machine learning. People arrive wanting it and it is usually the wrong next step; the data skills they now have are the bottleneck, not the models.

Streamlit is worth naming specifically. Seeing your own work as a web page is motivating in a way that another script is not.

The honest answer

How you actually get better from here

Build things you want to exist. Look up what you do not know as you need it. Read error messages carefully.

That is it. There is no course that substitutes for it, including this one. Twelve sessions got you to the point where the next thing you learn can come from needing it.

What not to do

Do not work through another twelve-week syllabus. You are past the stage where structured teaching is the fastest route, and tutorials feel productive in a way that building does not, which is exactly the trap.

What to do instead

Pick something slightly too hard, start it, and get stuck. The getting stuck is the learning. Everything you found hard in the last twelve weeks you now find easy, and that happened by being stuck and then not being stuck.

And keep the repo. It is a reference written in your own words, about your own confusions, which is better than any documentation.

This is the most important slide in the session. Say it plainly and do not soften it with a reading list.
