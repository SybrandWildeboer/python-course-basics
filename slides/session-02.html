Part one

Making decisions

So far every line has run, every time. Now we get to skip some.

Idea 1

Comparisons produce True or False

■

One = or two?

= puts a value into a variable. == asks whether two things are equal. Mixing them up is the single most common slip in this session, and Python will usually tell you off for it.

A value that is either True or False is called a boolean, after George Boole. That is the whole reason for the odd name.

Have them type if age = 41: on purpose to see the SyntaxError. Python's message here is unusually helpful and says "did you mean ==".

Idea 2

if: run this bit only sometimes

◆

Two things carry the meaning

The colon at the end of the if line, and the indentation of the lines under it. Indented lines belong to the if. The unindented line does not.

Four spaces is the convention. VS Code does it for you when you press Tab. Whatever you do, be consistent: mixing tabs and spaces gives you an IndentationError and hurts to look at.

In most languages indentation is decoration. In Python it is grammar. Say that explicitly, it reframes the whole thing.

Idea 3

elif and else: the other branches

Only one branch runs

Python checks top to bottom and stops at the first True. A score of 95 prints "Excellent" and never even looks at the other three.

So order matters a lot

Put score >= 50 first and everything above 50 is a "Pass", including 95. The bug runs perfectly and gives wrong answers, which is the worst kind.

else needs no condition. It is the "in every other case" branch, and it is optional.

The reordering bug is worth demonstrating live. Change the order, run it, watch a 95 become a Pass. Silent wrong answers are a theme of this course.

Idea 4

Combining conditions: and, or, not

WrittenTrue when
A and Bboth are true
A or Bat least one is true
not AA is false

Python reads almost like the English sentence you would say out loud. When a condition gets hard to read, that is usually a sign it is doing too much, not that you need to be cleverer.

Note for later: in pandas these become & and | with brackets, and that trips everybody up in session 8. Mention it exists, do not explain it.

Part two · 10 minutes

Let us break things on purpose

Errors are not the program telling you off. They are the most useful message you will get all day.

The habit

Read the last line first

  1. Last line. What kind of problem, and a short description. NameError: name 'price' is not defined means Python has never heard of price.
  2. The line number. line 4. That is where it gave up, and it is nearly always where the fix goes.
  3. The middle. The path through your program to get there. Today it is one line long. In a few sessions it will not be, and then it earns its keep.
◆

Everybody reads that wall of text from the top and gives up. Go straight to the bottom. This one habit will save you more time than any other thing in this course.

This is the highest-value slide in the whole twelve sessions. Do not hurry it. Have them say the last line out loud in their own words before touching the keyboard.

Part three

Repeating yourself

Computers are extremely good at doing the same dull thing ten thousand times. This is where that starts.

Idea 5

for: do this once per item

■

range(1, 6) stops before 6

The end is never included. It feels wrong for about a week and then it feels normal. range(5) gives you five numbers starting at zero.

The variable after for is yours to name. i is traditional for a counter, but for minute in ... is better when it means something.

Counting from zero will feel arbitrary. It pays off in session 4 with list positions, where my_list[0] is the first item. Promise them it connects, then move on.

Idea 6

The pattern you will use forever: accumulate

Three steps, every time

  1. Set up a variable before the loop
  2. Update it inside the loop
  3. Use it after the loop

The classic bug: putting total = 0 inside the loop. Then it resets every time round and your answer is always the last number. Try it, see it, remember it.

This pattern is homework task 2 and it reappears in session 4 as counting per category. Make sure they can write it without looking.

Idea 7

while: keep going until something changes

Which loop when?

for when you know how many, or you have a collection of things. while when you are waiting for a condition, like "until the guess is right".

■

Infinite loops, and how to escape

Forget count -= 1 and it runs forever. Press Ctrl C in the terminal to stop it. Do this on purpose now, so the first time it happens for real you shrug instead of panicking.

Make them write a real infinite loop and kill it with Ctrl+C. It takes twenty seconds and removes a genuine fear.

Idea 8

break and continue

Use it when you have found what you were looking for and the rest of the work is pointless.

i % 2 == 0 is the standard way to ask "is this even?". % gives the remainder after dividing.

◆

Both are optional conveniences. Anything you can do with them you can do with a cleverer condition, but they usually read better.

continue is the one people over-use. If they reach for it, check whether an if around the body would be clearer.

Style

When logic gets deep, flatten it

harder to follow
easier to follow
◆

Same behaviour, and the second one you can read top to bottom like a list of rules. Deal with the exceptions first, leave the happy path for last. When you find yourself three levels deep, that is the nudge to restructure.

They will write the left-hand version in the guessing game. Let them, then refactor it together. Showing the improvement beats asserting it.

Your turn · 40 minutes

Build the guessing game

◆ Live exercise

The computer picks a number from 1 to 100. You keep guessing. It says higher or lower.

Build it in this order

  1. Pick a secret number, print it while you build (cheat mode)
  2. Ask for one guess and say whether it is right
  3. Wrap it in a while loop so it keeps asking
  4. Add higher / lower feedback
  5. Count the guesses and report the count when they win
  6. Remove cheat mode

The one new thing you need

import brings in code somebody else wrote. randint(1, 100) includes both ends, unlike range. We do imports properly in session 4.

◆

File: sessions/session-02/exercises/guessing_game.py. Run it after every step. Six small working programs beat one big broken one.

Cheat mode first is the important trick: it makes the loop debuggable. Let them hit the int(input()) issue themselves, it is good revision from last week.

Stay quiet. Forty minutes is plenty, and struggling for five is fine.

Task 2 is the one that teaches. Highest and lowest need the same accumulate pattern as the total, with a comparison instead of an addition. If you get stuck on how to start the "highest so far" variable, that is exactly the right thing to be stuck on, and it is worth sitting with for a bit.

Do not tell them the trick for initialising highest and lowest. Starting at zero breaks on all-negative lists, and discovering that themselves is worth more than being told. Session 3 refactors this file into functions, so it needs to exist.

Wrap up

What you can do now

  • Compare values and get True or False
  • Branch with if, elif, else
  • Combine conditions with and, or, not
  • Loop a known number of times with for and range
  • Loop until something changes with while
  • Accumulate a result across a loop
  • Escape a loop with break, skip an item with continue
  • Read an error message from the bottom up
