Part one

What a database is

You already know the shape. This is the same table, kept somewhere better.

The idea

Tables, rows, columns, and a key

You have met all of this already

A table is your list of dictionaries. A row is one dictionary. A column is one key, and in a database every row has the same columns, with a fixed type.

The one new idea: a primary key

A column whose value is unique for every row, so you can point at exactly one row and nothing else. In our data, play_id and artist_id do that job.

"Relational" just means the tables can refer to each other, by those keys. That is next session, and it is where databases earn their keep.

Resist normalisation theory entirely. The useful version at this stage is "unique label per row", which is all they need to follow the joins next week.

Motivation

Why not just keep the CSV?

Size

Our file has 2,183 rows and Python reads it in a blink. At ten million rows, loading the whole thing into memory to answer one question stops being sensible.

Structure

A database knows minutes_played is a number. The CSV does not, which is why you were wrapping everything in float() last week.

Relationships

Artist details live once, in one table, instead of being repeated on every one of the 237 rows that mention them.

Many people at once

Several people, and several programs, can read and write safely together. Two people editing one CSV is a lost afternoon.

◆

The honest summary: CSV is a file, a database is a service. For a few thousand rows you could do all of today's work in Python. You are learning SQL because at work the data is already in a database, and because the language for asking questions is worth knowing in its own right.

Do not oversell databases. The honest framing, that this is where the data lives so this is the language you need, is more convincing than performance claims they cannot check.

Part two

Asking questions

Every query you write today is the same sentence with more clauses bolted on.

Clause 1

SELECT: which columns do you want?

Read it as a sentence

Which columns, from which table. That is the whole of SQL's shape, and everything else today is a refinement.

Conventions, not rules

  • Keywords in capitals so they stand out. SQL does not care
  • Semicolon at the end of a statement
  • Line breaks wherever they help. One clause per line reads best

SELECT * means every column. Handy when you are exploring, worth avoiding in anything you save: it breaks quietly when somebody adds a column.

Have them run SELECT * FROM plays first, so they see all 2183 rows arrive, then narrow it. The narrowing is what makes SELECT feel purposeful.

Clause 2

WHERE: which rows do you want?

■

Two things that catch everybody

  • One =, not two. In SQL a single = asks the question. == is a Python habit.
  • Single quotes for text. 'phone'. Double quotes mean something else in SQL, and the error will be confusing.

Dates here are text in YYYY-MM-DD form, which sorts and compares correctly as text. That is exactly why that format is worth insisting on.

The -- comment style is new to them; mention it in passing. The counts in the comments are real, so they can check their own results against the slide.

Clause 2, continued

Combining conditions

Exactly the and / or / not from session 2, in capitals. You already know how these behave.

▲

Brackets when you mix them

AND binds tighter than OR, so a OR b AND c means a OR (b AND c). That is rarely what you meant. Add the brackets and stop thinking about it.

Precedence bugs give a plausible-looking answer, which makes them expensive. The habit of bracketing mixed conditions is cheap insurance.

Clause 2, shortcuts

IN, BETWEEN, LIKE

All three are conveniences

IN saves a row of ORs. BETWEEN saves a >= and a <=. LIKE is the one with no plain equivalent.

Pattern characters

  • % any run of characters, including none
  • _ exactly one character
  • 'The %' starts with, '%Lines' ends with, '%Lines%' contains

BETWEEN includes both ends, unlike Python's range and slicing. One of the few places SQL is friendlier.

BETWEEN including both ends is worth calling out precisely because it contradicts the habit from sessions 2 and 4. Inclusive and exclusive ranges are a lifelong source of off-by-one errors.

Clause 2 · the trap

NULL is not a value, and = NULL never works

■

NULL means unknown, not zero and not empty text. Asking whether an unknown equals an unknown gives you "unknown", which is not true, so the row is not returned. No error, no warning, just an empty result that looks like an answer.

Real gaps in the artists table, so this is not hypothetical. Three artists have something missing.

Worth saying: aggregates skip NULLs, so AVG(formed_year) is the average of 38 values, not 40. That is usually what you want and occasionally a nasty surprise.

Clauses 3 and 4

ORDER BY and LIMIT

ORDER BY x DESC LIMIT 5 is the "top five" recipe, and it is probably the query shape you will type most often for the rest of your life.

Without ORDER BY, a database makes no promise about row order. LIMIT 5 on its own gives you five arbitrary rows, not the first five of anything.

The "no promise about order" point matters. SQLite happens to look stable, which teaches people a habit that breaks on a real database.

Clause 5

DISTINCT: what are the possible values?

The first thing to run on a new table

Before asking anything clever, ask what is actually in a column. It is how you find out that someone has been entering Phone, phone and PHONE, which is exactly what session 9 is about.

This is value_counts() in pandas, and it is your session 4 counting dictionary. Same question, third notation.

Frame DISTINCT as a data-inspection habit rather than a keyword. Running it on every categorical column of a new dataset is what experienced people do first.

Part three

Summarising

Up to now every query returned rows. Now we return answers about many rows at once.

Clause 6

Five functions that collapse many rows into one

AS renames a column

Without it the heading is literally ROUND(AVG(minutes_played), 2). Naming your output is a small courtesy to whoever reads it, including you.

COUNT(*) counts rows. COUNT(column) counts rows where that column is not NULL, which is a genuinely useful difference and an easy thing to get caught by.

COUNT(*) versus COUNT(column) comes back next session, where it is the difference between counting artists and counting artists who have plays.

Clause 7 · the big one

GROUP BY: one answer per group

◆

This is your session 4 counting dictionary. You wrote fifteen lines of Python with a dictionary and a .get() to get this table. Here it is one line. Same idea, and the database does the looping.

Put their own session 4 script next to this query on screen if you can. The comparison does more for their confidence in SQL than any explanation.

Clause 7 · the trap

Only group columns and aggregates in the SELECT

track_name is not grouped and not aggregated. There are 1,039 different track names in the phone group, so which one should appear? SQLite picks one at random and says nothing. Most other databases refuse outright, which is kinder.

▲

The rule: every column in your SELECT is either in the GROUP BY or wrapped in an aggregate. No exceptions, even though SQLite will let you break it.

Demonstrate the wrong version live so they see a plausible-looking result table with meaningless track names in it. Silent wrong answers are the theme worth hammering.

Clause 8

HAVING: filtering the groups

WHERE filters rows, before grouping

"Only look at plays from 2025." It happens first, on individual rows, and it cannot see a COUNT because no counting has happened yet.

HAVING filters groups, after grouping

"Only show countries with at least three artists." It happens after the aggregates exist, which is why it is the only one that can test a COUNT.

◆

You can use both in one query, and they do different jobs: WHERE played_at >= '2025-01-01' to narrow the rows, then HAVING COUNT(*) > 50 to narrow the groups.

Trying to use COUNT(*) in a WHERE is the error they will hit. The message names the problem reasonably well, and the fix is one word.
