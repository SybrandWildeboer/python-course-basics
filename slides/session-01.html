Part one · 10 minutes

What is Python?

Ten minutes, then we install. Enough to know what you are dealing with, not enough to be boring.

Definition

A general-purpose programming language

  • Created by Guido van Rossum, first released in 1991.
  • Designed around one conviction: code is read far more often than it is written, so readability wins over cleverness.
  • "General-purpose" means it is not a tool for one job. The same language does data analysis, file automation, websites, and scientific computing.
  • You learn it once and it follows you around for the rest of your career.
Readable, really

You can half-read that already, and you have written zero lines of Python. That is the whole design goal in one slide.

Do not go into the history of the name (Monty Python) unless asked. It is a fun fact that eats four minutes. Keep momentum toward the install.

Mental model

Your file is just text. The interpreter does the work.

This slide pays off next session. When an error appears with a line number, you want to be able to point back here: it got that far, then stopped.

Mental model

Two useful consequences

1 · Nothing to "build"

In some languages you compile first and run the result. Not here. You save the file and run it. Change one character, run it again.

That tight loop, edit, run, look, is how you will learn everything in this course.

2 · A program can fail halfway

Lines 1 to 7 ran. Line 8 was nonsense. Everything from line 8 never happened.

That is why error messages point at a specific line number, and why the output you already saw is still true.

◆

The habit that matters most in this whole course

When something breaks, read the last line of the error first, then look at the line number. We practise this properly next session.

Plant the flag here, do not teach it yet. Session 2 has ten minutes of deliberately breaking things.

A notebook is a list of cells

Some cells are text, some are code. You run a code cell and the answer appears directly underneath it. Then you write the next one.

Why that matters for learning

Two lines, run, look, two more lines. That loop is how you will learn everything here, and a notebook makes it as short as it goes.

Shift Enter runs a cell and moves on. Ctrl/Cmd Enter runs it and stays put.

Kernel selection is the one fiddly step. If VS Code cannot find a kernel, the fix is almost always pip install ipykernel, and VS Code usually offers to do it.

Do not explain markdown cells yet. They will notice the text cells are editable and ask, and that is a better moment for it.

Know this now

The one trap in notebooks

■

Cells remember what you ran, not what is on screen

Scroll up, change a cell, run it, and everything below is now out of date. The notebook will happily disagree with itself, and it looks completely normal.

The number beside a cell, [1], [2], tells you the order things actually ran in. When that order stops matching the order on screen, be suspicious.

The fix, and it is the whole fix

Restart and Run All, from the toolbar. It clears everything and runs the notebook from the top, in order.

And the standard to hold yourself to

If a notebook cannot run cleanly from top to bottom, it is not finished, however good the output looks on screen.

A runaway cell is stopped with the square interrupt button, which is the notebook version of Ctrl C.

Worth demonstrating: run a cell, delete the line that created a variable, run a later cell, and watch it still work. It is a thirty second demo that prevents a genuinely baffling afternoon later on.

Both, on purpose

Notebooks and scripts are for different jobs

A notebook, .ipynb
  • exploring, in small steps
  • the answer sits next to the code
  • learning something new
  • writing it up with prose and charts
A script, .py
  • somebody needs to run the thing
  • it asks questions, with input()
  • it runs start to finish, unattended
  • it gets scheduled, or shared as a tool
◆

Everything in this course exists in both shapes, so you can see the difference rather than take my word for it. Today's exercise is a good example: the notebook version is handed its values, the script version asks for them. Interactive programs want to be scripts.

◆

This is not a hard border. Most real work starts in a notebook and becomes a script once it is worth running again, and that is exactly what we do in session 10.

Do not let this become a philosophical discussion. The practical rule is enough: explore in a notebook, ship a script.

First code

Idea 1 of 7

print(): how a program talks to you

Note two things: print("Hello", "world") puts a space between the parts for you, and print(3 + 4) prints 7, because the maths happens before printing.

Have them deliberately forget a closing quote and a closing bracket now, quickly, to see what happens. Thirty seconds, then move on, because session 2 does errors properly.

Idea 2 of 7

Variables: a name for a value

◆

= means "put this in here"

It is not the = of mathematics. age = age + 1 is nonsense in algebra and perfectly ordinary here: work out the right-hand side, then store it under that name.

Naming rules and manners

  • Letters, digits, underscores. No spaces, cannot start with a digit.
  • Case matters: Name and name are two variables.
  • Use lower_case_with_underscores, and use real words: total_minutes, not tm.

The "a box with a label" metaphor is fine at this stage. Do not mention references or mutability. It will confuse, and it is not needed until lists in session 4.

Idea 3 of 7

Four types, and how to ask

TypeIsExample
strtext, "string of characters""Sam"
inta whole number41
floata number with a decimal point4.65
booltrue or false, nothing elseTrue
▲

"41" with quotes is text that happens to look like a number. 41 without quotes is a number. Python treats them completely differently, and this is the single most common beginner confusion.

"4" + "4" giving "44" is the slide that earns its keep. Let them predict the answer before you run it. Same with 10 / 4: dividing always gives a float, even when it comes out even.

Idea 4 of 7

f-strings: put values inside text

The f before the opening quote is the whole trick. Forget it and you get the literal text Hi {name}, which is a useful bug to recognise on sight.

Show the missing-f bug on purpose. It appears in their homework this week, guaranteed. The :.1f formatting will come back in session 9 for chart labels.

Idea 5 of 7

input() always hands you text

◆

Read the last line first

"unsupported operand for -: 'int' and 'str'" means you tried to subtract text from a number. Python is telling you exactly what is wrong, in its own vocabulary.

Even when the user types digits, input gives a str. Always. Say it twice. Then show the nesting: input runs first, int wraps the result, inside-out like brackets in maths.

Idea 6 of 7

Converting between types

■

Conversion can fail, loudly

int(4.99) is 4, not 5. It throws away everything after the point. When you want real rounding, say round().

The int() truncation bites people in financial and time calculations. Mention it now, it costs ten seconds.

Idea 7 of 7

Comments: notes for humans

Comment the why, not the what

The code already says what it does. Your comment should explain the decision, the unit, the assumption, or the thing you had to look up.

The second use: switching code off

Put a # in front of a line to stop it running without deleting it. Ctrl/Cmd / toggles it in VS Code. You will use this constantly while debugging.

Teach the comment shortcut key now. It turns into their main debugging tool for the next few weeks.

The four errors you will meet this week

MessageMeansFix
SyntaxErrorPython cannot even read the line, usually a missing quote, bracket or colonLook at the line and the one above it

▲

Watch out for smart quotes

If you paste code from a chat app or a document, you may get “curly quotes” instead of "straight quotes". Python only accepts the straight ones, and the difference is nearly invisible. When a SyntaxError makes no sense at all, retype the quotes by hand.
