Part one

A question you can finish

Projects rarely fail because the code was too hard. They fail because the question never stopped growing.

Where it starts

Start from the task you named in session 1

"One repetitive thing you do in a spreadsheet every week." It is the best starting point there is, because you already know what the answer is for.

The task

Every January I paste two years of listening side by side and build a pivot table per genre, by hand.

The answer you are after

Which genres I listen to more, and which less, than last year.

The question

Which genres did I listen to more in 2025 than in 2024, and which less?

The output

One CSV: minutes per genre in each year, and the change.

◆

The second card is the step people skip. Describing the steps of a task gives you a script that copies cells around. Describing the answer gives you a question, and a question tells you when you are done.

You wrote their task down in session 1. Read it back to them now. If it no longer fits (job changed, task disappeared), any question they genuinely care about will do, but push for one that repeats: it has a natural "done", and the script keeps paying off.

The test

What a project question looks like

QuestionVerdictWhy
"Analyse my listening habits"Not a question No question mark, no answer, no point at which it is finished
"What makes a song popular?"Too big Needs data you do not have, and researchers disagree about it
"Which genres grew, which shrank, by device, by month, by artist, and why?" Five questionsEach "and" is another project. Keep one.
"How many rows are in my file?"Too small One line of code. Nothing to decide, nothing to present
"Which genres did I listen to more in 2025 than in 2024, and which less?"Good One table answers it, the data exists, and you can say the answer in a sentence
  • Ends in a question mark
  • Answered by a number, a small table, or one chart
  • Answerable with data you have today
  • You care what the answer is

"You care" is not decoration. They will spend four or five evenings with this question; if the answer does not matter to them, the project will stall in week two.

The rule

One question. One dataset. One output.

That is the whole scope of a first project. Not a minimum to get past: the target.

Why so small

You have about two weeks of evenings before session 12. Real data takes longer than you think: the file reads wrong, a column means something other than its name, the dates are in two formats. A small project absorbs that. A big one collapses under it.

Small is not trivial

One question answered properly, with the cleaning decisions written down and the numbers checked, is more impressive than five answered roughly. It is also the only kind you can defend in ten minutes.

The words that make a project grow

  • "and also…"
  • "it would be nice if…"
  • "a dashboard"
  • "predict"
  • "from the API"
  • "once I get the data"

None of these are bad ideas. They are next projects. The next slide is where they go.

Say plainly that this is the rule you would apply to your own work. Experienced people scope small too; they are just better at noticing when they have stopped.

Sorting the ideas

Must, should, could, and won't

Must

The smallest thing that answers the question. If only this is done in session 12, the project succeeded.

Should

What makes it good. Usually the chart. Expected, but the project survives without it.

Could

If things go unexpectedly well. Nobody plans their week around a could.

Won't, this time

Good ideas you are deliberately not doing, written down so they stop nagging.

◆

Estimate each one, honestly

Must plus should should come to about six hours. If it is more, move something down a row. The plan has to survive a bad week.

◆

The won't list is the useful one

It is where scope creep goes to wait. A new idea mid-week goes on it, and the must carries on.

The won't list surprises people. Writing an idea down is what lets them stop thinking about it. Encourage a long one.

The one-number test: is the plan real?

Can you get a rough version of the must answer in about fifteen lines, today? Yes: the project is the right size. If you cannot even say what the number would be, the question is not ready yet.

unstack("year") turns the year label into columns: the table you would have built in the spreadsheet. And it adds up to 8,980.4 minutes, the raw total, so nothing was lost on the way.

The table rounds sixteen cells, so its total is 8,980.5 against 8,980.4 raw. If they spot that, good: a tenth is rounding, two hundred would be a bug. Knowing which is which is the skill.

What the first number is really for

It shows the decisions your question was making

I listened less overall. So part of every genre's "loss" is just that. Measure each genre as a share of the year instead, and:

Neither is wrong

They answer two slightly different questions. "Listened to more" means minutes, so the must uses minutes, and the share version goes on the could list.

project/pipeline.py

The first run: one stage at a time

  1. Run it unchanged. A known-good starting point.
  2. Point it at your file. Copy the data into project/data/, set INPUT and QUESTION, add sep or decimal to load if needed.
  3. Cut clean down to the columns you need and the one fix that stops it crashing. Real cleaning is milestone 1.
  4. Replace analyse with your rough answer, ending in .reset_index().
  5. Chart and check: rename their columns, or comment the calls out with a TODO.
  6. Run it, and open project/output/summary.csv.

Run it after every step

When something breaks, you then know exactly which change broke it. Six small steps beat one big edit every time.

The two traps here are reset_index (save_csv writes without the index, so labels in the index silently vanish) and check() expecting a plays column that their table no longer has. Both are in the notebook; mention them before they hit them.

The ambitious route

Your own Spotify history as the dataset

  1. On a computer, log in at spotify.com and open Account privacy, then Download your data.
  2. Tick Extended streaming history only. "Account data" gives just the last year, with fewer fields.
  3. Confirm the request from the email Spotify sends you.
  4. Wait for a second email with a link to a ZIP file.

It takes days

Spotify allows itself up to 30 days. People report anything from a few hours to two weeks. Request it today even if you are not sure, and start on other data if it has not arrived.

What you get

Your whole history since the account began, as JSON files named like Streaming_History_Audio_2024_0.json, plus a file called Read Me First that explains every field.

▲

Menu names on websites change. If the page does not match these steps exactly, look for "privacy" and "download your data" in your account settings.

Verified October 2026 against Spotify's support pages and several published guides; the exact page layout could not be checked without logging in. If they did not request it after session 10, they request it now, in the session, and the first run uses other data.

Before your next git add

Your data is not the course's data

project/data/ is ignored, on purpose

Anything you put there stays off GitHub by default. Keep your data in that folder: a file anywhere else would appear in git status, and git add . would send it. If your repository is public, everyone can read it, for ever.

What counts as private

Money, anything about other people, and exports like Spotify's, which include the IP addresses you streamed from.

◆

When in doubt, leave it out. Adding a file later is easy. Removing one from history once it is pushed is not.

Do this together, now, before the first commit of the day. Session 5's .gitignore lesson finally has real stakes. Small, non-private data can be committed, and then the project runs for anyone who clones it.
