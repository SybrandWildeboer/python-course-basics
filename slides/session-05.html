Part one

What a database is

You already know the shape. This is the same table, kept somewhere better.

The idea

Tables, rows, columns, and a key

You have met all of this already

A table is your list of dictionaries. A row is one dictionary. A column is one key, and in a database every row has the same columns, with a fixed type.

The one new idea: a primary key

A column whose value is unique for every row, so you can point at exactly one row and nothing else. In our data, play_id and artist_id do that job.

"Relational" just means the tables can refer to each other, by those keys. That is after the break, and it is where databases earn their keep.

Resist normalisation theory entirely. The useful version at this stage is "unique label per row", which is all he needs to follow the joins after the break.

Part two

Asking questions

Every query you write today is the same sentence with more clauses bolted on.

Clause 1

SELECT: which columns do you want?

Read it as a sentence

Which columns, from which table. That is the whole of SQL's shape, and everything else today is a refinement.

Conventions, not rules

  • Keywords in capitals so they stand out. SQL does not care
  • Semicolon at the end of a statement
  • Line breaks wherever they help. One clause per line reads best

SELECT * means every column. Handy when you are exploring, worth avoiding in anything you save: it breaks quietly when somebody adds a column.

Have them run SELECT * FROM plays first, so they see all 2183 rows arrive, then narrow it. The narrowing is what makes SELECT feel purposeful.

Clause 2

WHERE: which rows do you want?

■

Two things that catch everybody

  • One =, not two. In SQL a single = asks the question. == is a Python habit.
  • Single quotes for text. 'phone'. Double quotes mean something else in SQL, and the error will be confusing.

Dates here are text in YYYY-MM-DD form, which sorts and compares correctly as text. That is exactly why that format is worth insisting on.

The -- comment style is new to them; mention it in passing. The counts in the comments are real, so they can check their own results against the slide.

Clause 2, continued

Combining conditions

Exactly the and / or / not from session 2, in capitals. You already know how these behave.

▲

Brackets when you mix them

AND binds tighter than OR, so a OR b AND c means a OR (b AND c). That is rarely what you meant. Add the brackets and stop thinking about it.

Precedence bugs give a plausible-looking answer, which makes them expensive. The habit of bracketing mixed conditions is cheap insurance.

Clause 2, shortcuts

IN, BETWEEN, LIKE

All three are conveniences

IN saves a row of ORs. BETWEEN saves a >= and a <=. LIKE is the one with no plain equivalent.

Pattern characters

  • % any run of characters, including none
  • _ exactly one character
  • 'The %' starts with, '%Lines' ends with, '%Lines%' contains

BETWEEN includes both ends, unlike Python's range and slicing. One of the few places SQL is friendlier.

BETWEEN including both ends is worth calling out precisely because it contradicts the habit from sessions 2 and 4. Inclusive and exclusive ranges are a lifelong source of off-by-one errors.

Clause 2 · the trap

NULL is not a value, and = NULL never works

■

NULL means unknown, not zero and not empty text. Asking whether an unknown equals an unknown gives you "unknown", which is not true, so the row is not returned. No error, no warning, just an empty result that looks like an answer.

Real gaps in the artists table, so this is not hypothetical. Three artists have something missing.

Worth saying: aggregates skip NULLs, so AVG(formed_year) is the average of 38 values, not 40. That is usually what you want and occasionally a nasty surprise.

Clauses 3 and 4

ORDER BY and LIMIT

ORDER BY x DESC LIMIT 5 is the "top five" recipe, and it is probably the query shape you will type most often for the rest of your life.

Without ORDER BY, a database makes no promise about row order. LIMIT 5 on its own gives you five arbitrary rows, not the first five of anything.

The "no promise about order" point matters. SQLite happens to look stable, which teaches people a habit that breaks on a real database.

Clause 5

DISTINCT: what are the possible values?

The first thing to run on a new table

Before asking anything clever, ask what is actually in a column. It is how you find out that someone has been entering Phone, phone and PHONE, which is exactly what session 6 is about.

This is value_counts() in pandas, and it is your session 4 counting dictionary. Same question, third notation.

Frame DISTINCT as a data-inspection habit rather than a keyword. Running it on every categorical column of a new dataset is what experienced people do first.

Part three

Summarising

Up to now every query returned rows. Now we return answers about many rows at once.

Clause 6

Five functions that collapse many rows into one

AS renames a column

Without it the heading is literally ROUND(AVG(minutes_played), 2). Naming your output is a small courtesy to whoever reads it, including you.

COUNT(*) counts rows. COUNT(column) counts rows where that column is not NULL, which is a genuinely useful difference and an easy thing to get caught by.

COUNT(*) versus COUNT(column) comes back after the break, where it is the difference between counting artists and counting artists who have plays.

Clause 7 · the big one

GROUP BY: one answer per group

◆

This is your session 4 counting dictionary. You wrote a loop with a dictionary and a .get() to get a table like this. Here it is one line. Same idea, and the database does the looping.

Put his own session 4 script next to this query on screen if you can. The comparison does more for their confidence in SQL than any explanation.

Clause 7 · the trap

Only group columns and aggregates in the SELECT

track_name is not grouped and not aggregated. There are 1,039 different track names in the phone group, so which one should appear? SQLite picks one at random and says nothing. Most other databases refuse outright, which is kinder.

▲

The rule: every column in your SELECT is either in the GROUP BY or wrapped in an aggregate. No exceptions, even though SQLite will let you break it.

Demonstrate the wrong version live so they see a plausible-looking result table with meaningless track names in it. Silent wrong answers are the theme worth hammering.

Clause 8

HAVING: filtering the groups

WHERE filters rows, before grouping

"Only look at plays from 2025." It happens first, on individual rows, and it cannot see a COUNT because no counting has happened yet.

HAVING filters groups, after grouping

"Only show countries with at least three artists." It happens after the aggregates exist, which is why it is the only one that can test a COUNT.

◆

You can use both in one query, and they do different jobs: WHERE played_at >= '2025-01-01' to narrow the rows, then HAVING COUNT(*) > 50 to narrow the groups.

Trying to use COUNT(*) in a WHERE is the error they will hit. The message names the problem reasonably well, and the fix is one word.

Part four · after the break

Why the data is in pieces

Before the break everything came from one table. That was not an accident of the data.

The reason

Why not keep everything in one big table?

Three problems, all the same problem

  • Waste: Norway written 237 times
  • Drift: fix a typo in one row and 236 rows still disagree
  • Nowhere to put a fact: an artist you have not listened to yet cannot exist at all

So each fact lives in exactly one place

An artist's country is a fact about the artist, so it belongs in artists, once. A play is a fact about one listen, so it belongs in plays.

The cost of that tidiness

Most interesting questions now need both tables at once. "How many minutes per country" touches a column in each. Putting them back together for the length of one query is what a join is.

Your session 4 CSV had the artist details repeated on every row. That was deliberate, to keep it to one file. Real databases do not look like that.

The "nowhere to put a fact" point is the one people have not thought of, and it is why our two never-played artists exist in the data.

Vocabulary

Primary keys and foreign keys

A primary key identifies a row in its own table. One artist, one artist_id.

A foreign key is a column that points at another table's primary key. It is the same number, borrowed, and it is what a join matches on.

The word "foreign" just means "belongs to another table". Say that; the name puts people off more than the idea does.

Your first join

Now the names come back

Read the ON as the rule

"Bring me the artists row whose artist_id matches this play's artist_id." That is all a join is: a matching rule between two tables.

AS p and AS a are aliases, short nicknames for the tables. p.track_name then says which table a column came from.

Every query before the break could only show an artist_id, because the name was out of reach. Run this and let him see the names arrive. It is a satisfying moment.

Mental model

What the database actually does

This slide is the groundwork for the fan-out block. Make sure they see that one play row can pair with more than one row from the other side, because that is exactly what goes wrong later.

Notation

Two conveniences worth knowing

Ambiguous columns need qualifying

USING, when the columns share a name

Use USING when the key has the same name on both sides, which is common and is why our tables are named that way. ON works always, including when the names differ.

◆

Get in the habit of aliasing every table and qualifying every column, even when you do not have to. Queries grow, and the day you add a third table you will be glad the first two were already labelled.

"Ambiguous column name" is the error of the day. It is clear once you have seen it once, which is why it is on a slide.

The second kind

LEFT JOIN: keep the rows with no match

"Left" means the first table listed

Every row of the left table survives. Where the right table has no match, its columns come back as NULL instead of the row being dropped.

◆

The question decides which one

"How long did I listen to each artist I played" is an inner join. "Which artists have I never played" needs a left join, because the answer is made entirely of rows that have no match.

Two artists in the data have no plays at all, deliberately, so this is a real result and not a hypothetical. That is the next slide.

Why you should care

The two artists the inner join hides

Why COUNT(p.play_id) and not COUNT(*)

After a left join, an unmatched artist still produces one row, with all the plays columns NULL. COUNT(*) counts that row and says 1. COUNT(p.play_id) skips NULLs and correctly says 0.

▲

That is the COUNT(*) versus COUNT(column) difference from before the break, and this is where it earns its keep. Change one word and "never played" becomes "played once".

Run it both ways live. COUNT(*) giving 1 for an artist with no plays is exactly the kind of bug that looks like data and is really a query mistake.

Part five · the real lesson

How a join makes your numbers wrong

This is the part to remember in five years, when everything else here has faded.

A true story that happens constantly

Two queries. One number changed.

the total minutes
the same total, with awards joined on
■

Nothing was filtered. Nothing was added. The total went up by 751 minutes.

Both queries ran without a word of complaint. If you had only ever run the second one, you would have reported 9,732 and nobody in the room could have told you otherwise.

Let this sit for a moment before explaining. The discomfort is the point: a query that runs is not a query that is right.

The diagnosis

Count the rows, and it is obvious

Every play met every award

The join has no idea the awards are unrelated to the listening. It only follows the rule you gave it: match on artist_id. Three awards means each play appears three times, and its minutes get counted three times.

This is called fan-out

A one-to-many join multiplies rows. Across the whole dataset, 2,183 plays became 2,371 rows, and every SUM, COUNT and AVG downstream is wrong.

The habit worth building: after any join, check the row count against what it was before. If it went up and you did not expect it to, stop.

846.2 times 3 is 2538.6, and the query says 2538.5. The difference is rounding on individual values. Worth mentioning only if they spot it, as a nice piece of arithmetic checking.

A trap inside the trap

"Just use DISTINCT" does not fix it either

QueryAnswerRight?
No join846.2Yes
Joined2538.5Three times too big
Joined with SUM(DISTINCT)680.6 Too small now

SUM(DISTINCT) adds up each different value once. Two separate plays that both happened to last 4.65 minutes are two real plays, and it throws one away. It fixed the duplication and destroyed the data.

◆

The lesson is bigger than the keyword. When a number looks wrong, do not reach for the switch that makes it look right. Work out what the rows actually are first. Here, two wrongs sat either side of the correct answer, and both looked like fixes.

This slide is the most valuable in the session and possibly the course. Nearly every beginner reaches for DISTINCT; almost nobody checks whether it is the right tool.

Doing it properly

Aggregate first, then join

Why this works

per_artist reduces plays to one row per artist before anything else touches it. After that the awards join cannot duplicate a play, because there are no play rows left to duplicate.

WITH name AS (...) is a CTE, a common table expression: a query with a name, used like a table below it. You can have several, separated by commas.

Fjord & Flint 846.2 with 3 awards, matching the standalone query exactly. Point at that: the fix is verified by an independent calculation, not by looking plausible.

The same thing written as a subquery nested in the FROM, and views, are in stretch 7. Push CTEs: beginners can adopt them immediately and then never write a deeply nested subquery at all.

Reference · keep this one

When the numbers look wrong

SymptomLikely causeCheck
Totals larger than they should beFan-out from a one-to-many join Count rows before and after the join
Rows have gone missingAn inner join where you needed a left join Swap to LEFT JOIN and compare counts
Everything is zero or emptyThe join keys do not actually match Compare a few values from each side by eye
Counts are one too many per groupCOUNT(*) after a left join Use COUNT(the_other_table.key)
A percentage comes out as 0Whole-number division Multiply by 100.0 first
◆

Above all: know roughly what the answer should be before you run the query. 8,980 minutes over two years is about twelve minutes a day, which is plausible. 9,732 would have passed unnoticed without a number to compare it to. An expectation is the cheapest bug detector you have.

Wrap up

What you can do now

  • Choose columns with SELECT and rows with WHERE
  • Handle NULL without being fooled by it
  • Sort, cut and list values: ORDER BY, LIMIT, DISTINCT
  • Answer per-group questions with GROUP BY
  • Filter groups with HAVING, and say how it differs from WHERE
  • Tell a primary key from a foreign key
  • Choose between an inner and a left join, on purpose
  • Join and then aggregate
  • Spot fan-out, and explain it
  • Fix it by aggregating first in a CTE, not with DISTINCT
