# Instructor notes

How to run this course. The per-session run sheets live in
`sessions/session-NN/README.md`; this is the course-wide stuff.

---

## The shape of the course

Twelve two-hour sessions, one to one, online, with two to four hours of homework in between.
One dataset the whole way through, and a project the learner chooses in session 11 and
presents in session 12.

| # | Session | Core skill |
|---|---|---|
| 1 | Setup and first contact | Environment, notebooks, variables, types, f-strings |
| 2 | Control flow | if/else, loops, reading error messages |
| 3 | Functions | def, return versus print, scope |
| 4 | Lists, dictionaries and files | Data structures, CSV in and out |
| 5 | Git and GitHub | Commits, branches, pushing to their own repo |
| 6 | SQL foundations | SELECT, WHERE, GROUP BY, HAVING |
| 7 | Joins and shaping | Joins, CTEs, fan-out |
| 8 | pandas | DataFrames, filtering, groupby, merge |
| 9 | Cleaning and visualization | Missing data, types, matplotlib |
| 10 | Putting it together | Pipeline script, venv, project structure |
| 11 | Project scoping and setup | Scope, milestones, a first working run |
| 12 | Presentation and next steps | Review, and the map ahead |

## How each session runs

| Time | What |
|---|---|
| 0:00–0:15 | Homework review, **especially what broke** |
| 0:15–0:50 | New material, in small chunks, with them typing along |
| 0:50–1:00 | Break |
| 1:00–1:50 | They build something, you watch and nudge |
| 1:50–2:00 | Commit, homework briefing, questions |

**They share their screen and they drive.** The main online failure mode is you demonstrating
fluently while they nod along. If you are typing, they are not learning.

**Homework is always two tasks:** one they can definitely finish, one they probably cannot.
The second is what you open the next session with.

## The Saturday check-in

From session 1, agree a standing Saturday message. One line, nothing more:

> "Homework done" or "Homework not done"

No explanation needed, no guilt attached. It exists so you know whether to adjust the next
session, and so a week does not disappear silently.

**Tell them explicitly that "not done" is a completely acceptable answer.** The check-in only
works if it is cheap to send. The first time they skip it out of embarrassment, the
mechanism is dead.

## Notebooks, and why the scripts are still there

Notebooks are the primary surface. Every session has a `notebooks/` folder, and everything
also exists as a plain `.py` script.

That is deliberate rather than duplication: a notebook is for exploring, a script is for
running, and having both makes the difference concrete rather than asserted. Session 1 has a
slide on it, session 10 is about making the move on purpose, and session 5 covers why
notebooks and git get along badly.

**Anything interactive is script-only.** The session 2 guessing game and the session 3 menu
program ask the user questions, and `input()` in a notebook is awkward. That contrast is part
of the lesson.

## The dataset

One dataset carries the whole course: a listening log of 2,183 plays across 40 artists and
two years. It appears in four shapes: clean CSVs, a SQLite database with three tables, a
deliberately messy CSV, and as the input to the session 10 pipeline.

It is generated by a seeded standard-library script, so the numbers on the slides always
match the numbers on their machine. Regenerate any time with:

```bash
python3 data/scripts/build_dataset.py
```

Three things in it are there on purpose:

- **two artists have no plays at all**, so `LEFT JOIN` has something real to show
- **the `awards` table is one-to-many**, which is what makes the session 7 fan-out
  demonstration work on real data
- **three artists have missing values** in the lookup table, so `IS NULL` is not
  hypothetical

If you change the dataset, run `python3 tools/check_sql.py` and
`python3 tools/nbtool.py run` afterwards: several slides quote exact figures and the checkers
verify them.

### If they want to use their own data

Better, if they care about it. Requirements: a few thousand rows at most, at least one date
column, one numeric column, a few categorical columns, and something that can become a second
related table for session 7.

Decide before session 6, when the database appears. You will have to translate the exercises,
which is real work, so weigh it against how much the motivation is worth.

## The five highest-value moments in the course

If time is short, protect these.

1. **Session 2, reading errors.** Ten minutes of deliberately breaking things and reading the
   messages. It is the single highest-value block in twelve sessions.
2. **Session 3, return versus print.** Do not move on until they can predict all six outputs
   on slide 7. `None + 1` failing is the moment it clicks.
3. **Session 4, "a list of dictionaries is a table".** The hinge of the whole course. CSV, SQL
   and pandas are all this shape.
4. **Session 7, fan-out.** The lesson they will still be using in ten years, including the
   `SUM(DISTINCT)` trap that produces a second wrong answer.
5. **Session 9, the date trap.** A convenient one-liner that silently corrupts 29% of the
   data. Nothing else in the course makes the "verify, do not assume" point so vividly.

## The through-line worth naming out loud

The same question, in three notations:

| Session | How you count plays per genre |
|---|---|
| 4 | a dictionary and `.get()`, fifteen lines of Python |
| 6 | `GROUP BY genre`, one line of SQL |
| 8 | `groupby("genre")`, one method call |

Saying "same idea, three notations" turns SQL and pandas into translations rather than new
subjects. Sessions 6 and 8 both have a side-by-side slide for exactly this.

## Checking the materials

If you edit anything:

```bash
python3 tools/check_slides.py     # every slide fits, no overflow, notes present
python3 tools/check_sql.py        # every query runs and returns the row count claimed
python3 tools/nbtool.py check     # notebooks valid, no saved output
python3 tools/nbtool.py run       # every notebook still runs top to bottom
```

The checkers need a couple of extras:

```bash
pip install playwright nbformat nbclient ipykernel
playwright install chromium
```

`check_sql.py` verifies the row counts pinned in `-- expect: N rows` comments. It has already
caught several figures that were written from estimate rather than from the data, which is
exactly what it is for.

## Running the slides

```bash
python3 serve.py
```

In a deck: arrows to move, `o` for a grid of every slide, `n` for **speaker notes**, `t` for
light or dark, `f` for full screen, `p` to print or export as PDF, `?` for the full list.

**Use the speaker notes.** Every slide has them, and they carry the things that are not on
the slide: what to demonstrate live, what to let them struggle with, what not to mention yet.

## Tone

The decks are deliberately warm and deliberately direct. Two things are worth keeping:

- **No em dashes anywhere.** A house style choice; keep it if you edit.
- **Encouragement should be specific.** "Your `clean()` docstring records the decisions, which
  most professionals do not bother with" is worth ten times "good job".

## What not to teach

Deliberately absent, because they cause more confusion than they solve at this stage:

- `git reset --hard`. It genuinely destroys work, and `git restore` and `git revert` cover
  what they need.
- `global`. If they find it, say it exists, that it is almost always the wrong tool, and
  steer back to parameters and return values.
- Mutable default arguments. A real Python trap and completely wrong for session 3.
- `inplace=True` in pandas. Tell them not to, and why, and move on.
- Classes. Nothing in this course needs them, and they are a session of their own.
- Views and copies in pandas. Teach the `.loc` habit that prevents the warning instead.
